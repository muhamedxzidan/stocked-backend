# تسجيل الدخول والجلسات — API المرحلة الحالية

الحالة: منفذ محليًا. هذه مرحلة المصادقة، وليست اكتمال نظام المخزن أو جاهزية الإنتاج.

## التشغيل بالترتيب

داخل stocked-backend:

```bash
npm ci
npx prisma generate
docker compose up -d
npx prisma migrate deploy
npm run admin:bootstrap
npm run start:dev
```

قبل ذلك انسخ .env.example إلى .env إن لم يكن موجودًا واضبط بيانات PostgreSQL المتطابقة مع Docker.
يجب توليد AUTH_RATE_LIMIT_SECRET عشوائيًا (32 بايت على الأقل):

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

ضع الناتج في .env فقط، واستخدم نفس السر عبر نسخ البيئة الواحدة؛ لا ترفعه إلى Git.
في جهاز التطوير الحالي تم إضافة سر محلي تلقائيًا دون عرضه أو حفظه في ملفات المشروع المتتبعة.
تغيير سر العدادات يبدأ نطاق مفاتيح جديدًا، لذلك لا تستخدم تدويره المتكرر كطريقة لتجاوز حدود المحاولات.

أمر admin:bootstrap يبني التطبيق ويطلب البريد والاسم وكلمة المرور والتأكيد بإدخال مخفي. يعمل في Terminal تفاعلي فقط، ويمنع التهيئة إذا وجدت أي حسابات. لم يشغل هذا الأمر على قاعدة التطوير ضمن تنفيذ المرحلة؛ لا مدير افتراضي ولا كلمة مرور معروفة.
أول مدير ملزم بتغيير كلمة المرور بعد الدخول. لا endpoint للتسجيل الذاتي أو لإنشاء أول مدير.

## العناوين

- API: http://127.0.0.1:3000/api/v1
- جاهزية القاعدة: GET /api/v1/health
- Swagger للتطوير: http://127.0.0.1:3000/api/docs
- OpenAPI JSON للتطوير: /api/docs-json
- عند NODE_ENV=production لا توجد واجهة Swagger أو وثيقتها.
- HOST الافتراضي 127.0.0.1؛ إعداد نشر السيرفر يحدد الواجهة وTLS بشكل مستقل.

## 1. الدخول

POST /api/v1/auth/login

```json
{ "email": "admin@example.com", "password": "<your private password>" }
```

البريد يطبّع إلى lowercase مع trim. كلمة المرور لا تتغير ولا تقتطع.
الاستجابة 200:

```json
{
  "token": "<opaque session secret returned once>",
  "tokenType": "Bearer",
  "expiresAt": "<UTC ISO timestamp>",
  "user": {
    "id": "<UUID>",
    "email": "admin@example.com",
    "displayName": "Admin",
    "role": "ADMIN",
    "merchantId": null,
    "mustChangePassword": true
  }
}
```

لا تدخل كلمة مرور حقيقية في وثيقة أو أمر قابل للحفظ في سجل Terminal. أمثلة المستند وصفية وليست بيانات حساب جاهز.
يقدم Swagger حقول الطلب وعقد الاستجابة، والرمز يضاف من Authorize عند التجربة. حفظ التفويض في Swagger معطل.

## 2. الحساب الحالي

GET /api/v1/auth/me

```text
Authorization: Bearer <session token>
```

الاستجابة 200 تحتوي حقول user الستة الموضحة أعلاه فقط. الهوية تأتي من قاعدة البيانات الحالية، ولا يمكن تمرير role أو merchantId لتغييرها.

## 3. تغيير كلمة المرور

POST /api/v1/auth/change-password، بنفس ترويسة التفويض.

```json
{
  "currentPassword": "<current private password>",
  "newPassword": "<different private password, 15–128 characters>"
}
```

يرجع عقد الدخول نفسه بجلسة جديدة، وتصبح mustChangePassword=false. تبطل كل جلسات الحساب السابقة داخل نفس المعاملة. يستبدل العميل الرمز بعد نجاح الاستجابة.
إذا فشل حفظ الجلسة الجديدة تتراجع كلمة المرور والإبطالات؛ لا تغيير جزئي.
إذا نفذ تغييران بالتزامن ينجح واحد ويطلب الآخر تسجيل الدخول مجددًا.
يطبق حد محاولات الحساب والمصدر أيضًا على تغيير كلمة المرور لمنع تجربة الحالية بلا حد.

## 4. الخروج

POST /api/v1/auth/logout، بنفس ترويسة التفويض.

يرجع 204 دون جسم، ويبطل الجلسة الحالية في الخادم. استخدام الرمز بعدها يرجع 401. حذف الرمز من العميل لا يقوم مقام الإبطال.

## الأخطاء والمدخلات

| الحالة | المعنى |
|---|---|
| 400 | DTO غير صحيح أو حقول زائدة أو سياسة كلمة مرور غير مستوفاة أو JSON غير صالح |
| 401 | فشل دخول عام، رمز غير صالح/مبطل/منته، حساب أو تاجر معطل، أو كلمة حالية غير صحيحة |
| 403 | منع دور أو endpoint غير مصرح صراحة أو إلزام تغيير كلمة المرور |
| 413 | جسم الطلب أكبر من 16 KiB |
| 429 | محاولات زائدة؛ Retry-After عدد الثواني المطلوبة |
| 500 | فشل داخلي عام دون stack trace أو تفاصيل قاعدة البيانات |
| 503 | فشل اتصال DB في health |

استجابات API تحمل Cache-Control: no-store. لا passwordHash أو tokenHash في أي استجابة.
الرسالة نفسها لفشل البريد المجهول أو الحساب المعطل أو كلمة الدخول الخاطئة. هذا يقلل كشف الحسابات، ولا يمثل ضمانًا لتطابق زمن كل طلب على الشبكة.

## سياسة الجلسة والتفويض

- 32 بايت عشوائية crypto؛ يحفظ SHA-256 digest فقط.
- مدة مطلقة أقصاها 12 ساعة، وخمول أقصاه 30 دقيقة. النشاط لا يمد المدة المطلقة.
- يعاد فحص الحساب والدور والتاجر والجلسة مع كل طلب. إلغاء نشاط المستخدم أو التاجر يمنع جلسة قائمة.
- جلسة mustChangePassword=true تسمح فقط بـme وتغيير كلمة المرور والخروج ضمن API المصادقة؛ health العامة لا تقدم بيانات الحساب.
- كل route محمية افتراضيًا، ويجب إعلان Authenticated أو Roles. المعلومة الغائبة لا تعني السماح.
- فحص الدور لا يحقق وحده ملكية السجل؛ عزل مخزون كل تاجر سينفذ في استعلامات ميزات الأعمال ويختبر حينها.
- معاملات الجلسات وتغيير كلمة المرور تقفل صف المستخدم نفسه، وتعيد التحقق قبل الكتابة، حتى لا ينشئ دخول متزامن جلسة اعتمادًا على كلمة قديمة.
- endpoints إدارة الحسابات والأدوار والتعطيل وحماية آخر مدير أصبحت منفذة، وتعيد التفويض داخل معاملة بقفل وإبطال متوافقين؛ انظر [دليل الإدارة](admin-api.md).

## حماية محاولات الدخول

عدادان داخل PostgreSQL: للحساب وللمصدر، مفاتيحهما HMAC من سر البيئة؛ لا بريد أو IP خام في الجدول.
الحد الافتراضي 5 محاولات لكل حساب و20 لكل مصدر خلال نافذة 15 دقيقة. تحسب المحاولات الناجحة والفاشلة والطلبات ذات DTO غير صحيح إذا كان جسم JSON قابلًا للتحليل؛ لا قفل دائم.
العدادات ذرية ومشتركة بين نسخ الخادم. يفحص عداد المصدر أولًا بترتيب أقفال ثابت؛ إذا تجاوز الحد يحتسب المصدر فقط، ولا تنشأ عدادات حساب جديدة بطلب بريد مختلف. المحاولة المحظورة تحسب أيضًا، لكن لا تمد انتهاء النافذة.
التأخير يتدرج بحد 150 ms بعد إغلاق المعاملة؛ لا يضمن وحده الحماية من كل صور إساءة الخدمة.
عناوين X-Forwarded-For لا تثق بها الإعدادات المحلية. TRUSTED_PROXIES تقبل قائمة المصادر/CIDRs الفعلية للـreverse proxy فقط؛ لا قائمة شاملة.

لتنظيف العدادات المنتهية:

```bash
npm run auth:cleanup
```

النافذة تنتهي وتعمل مجددًا حتى دون التنظيف؛ يلزم تشغيل صيانة دورية وقت النشر لتقييد نمو الجدول. لا يوجد job مجدول تلقائيًا الآن.

## كلمات المرور

Argon2id بمعلمات memoryCost=19456 KiB، timeCost=2، parallelism=1. يقاس الأداء عند اختيار حجم السيرفر دون تقليل الحد الأمني اعتباطًا.
الطول 15–128 Unicode code points. لا إزالة مسافات، ولا تغيير لحالة أحرف كلمة المرور المحفوظة.
القائمة المحلية المثبتة من SecLists (MIT) تمنع الكلمات الشائعة عند التطابق الكامل دون حساسية لحالة الأحرف؛ مصدرها ونسختها وSHA256 وترخيصها داخل src/auth/data/.
القائمة ليست قاعدة كاملة لكلمات المرور المسربة؛ لا خدمة كشف تسريب خارجية في هذا التنفيذ. زيادة التغطية تحتاج قائمة معتمدة أكبر أو شريحة فحص اختراقات محددة قبل إطلاق عام.
لا تجلب قوائم من الإنترنت أثناء الدخول أو التشغيل.

## الاختبارات

```bash
npm run build
npm run lint
npm test
npm run test:e2e
npm run test:db
npx prisma validate
npx prisma migrate status
```

test:e2e يستورد كود Nest المبني للحفاظ على decorator metadata كما في الإنتاج، وينشئ قاعدة stocked_auth_test_<random> محلية، يطبق الترحيلات، ثم يحذفها. test:db يحتفظ بعزل stocked_identity_test_<random>.
كلاهما يرفض مصدرًا غير localhost/127.0.0.1 وstocked_dev ويحتاج CREATE DATABASE؛ لا يشغل بحساب إنتاج.
اختبارات الأدوار تستخدم controllers موجودة في ملفات الاختبار فقط؛ لا routes تجريبية في التطبيق.

## الحدود الحالية قبل النشر

- إدارة المستخدمين والتجار أصبحت متاحة للمدير؛ استعادة كلمة المرور وقواعد المخزون والشحن والمرتجعات لم تنفذ بعد.
- النقل الحالي Bearer للـAPI والعميل الأصلي. Cookie/CSRF وسياسة CORS للمتصفح شريحة تالية قبل ربط واجهة ويب؛ لا تخزن رموز الدخول في localStorage.
- npm audit وnpm audit --omit=dev سجلا 4 تحذيرات high عبر prisma/@prisma/config/deepmerge-ts/mysql2، رغم إزالة أداة Mau غير المستخدمة. تصنف peer dependency Prisma ضمن شجرة التدقيق؛ لا ندعي خلو التشغيل من التحذيرات بمجرد حذف devDependencies.
- Prisma 7.10.0 يثبت deepmerge-ts 7.1.5 وmysql2 3.15.3. إصلاح التدقيق المقترح بالقوة يخفض Prisma إلى 6؛ لم يطبق. أي override رئيسي يحتاج مراجعة توافق مستقلة، وهذه نقطة مفتوحة قبل النشر.
- التطبيق يستخدم PostgreSQL، لكن ذلك لا يحذف تحذير اعتماد MySQL المتضمن في Prisma ولا يعادل معالجة الثغرة.
- مطلوب TLS وإعداد proxy موثوق ومستخدم DB runtime محدود ومستخدم migration منفصل ونسخ احتياطي واستعادة وإدارة أسرار وفحص تحميل قبل الإنتاج.
- فحص حالة الحساب في guard يخص بداية الطلب؛ عمليات الأعمال المستقبلية تعيد التفويض داخل معاملة الكتابة مع قواعد التعطيل، فلا يعد هذا ضمانًا ذريًا لكل عملية أعمال غير منفذة.
