# دليل الأصناف والباركود

الحالة: منفذ في الباك اند بتاريخ 9 أكتوبر 2026، وفق المخطط المعتمد. لا تعديل في Flutter.

## ما تم تنفيذه

كل صنف يتبع تاجرًا واحدًا وله هوية وكود ثابت مثل MZ-000001. عداد مستقل لكل تاجر؛ بعد MZ-999999 يأتي MZ-1000000. رمز التاجر ثابت مسبقًا. نفس السلعة عند تاجر آخر صنف مستقل وكود مستقل.

إنشاء صنف يضيف بيانات تعريفية فقط؛ لا ينشئ كمية أو رصيدًا أو حركة. الكميات تُضاف لاحقًا عبر الاستلام الفعلي. لا حسابات أو أصناف افتراضية أو بيانات تشغيل تجريبية.

## الصلاحيات

| العملية | المدير | أمين المخزن | الموظف | التاجر |
| --- | --- | --- | --- | --- |
| إنشاء صنف لتاجر نشط | نعم | نعم | نعم | لا |
| القراءة والبحث وبيانات الملصق | كل التجار | كل التجار | كل التجار | أصنافه فقط |
| تعديل الوصف أو التعطيل والتفعيل | نعم | لا | لا | لا |
| تغيير المالك أو الكود أو الحذف | لا | لا | لا | لا |

كل المسارات تحتاج Bearer session صالحًا وإتمام تغيير كلمة المرور الإلزامي. الصلاحيات من الخادم. قائمة التاجر والتفاصيل والكود والملصق كلها مقيدة بـmerchantId من حسابه؛ محاولة قراءة صنف تاجر آخر ترجع 404. تمرير فلتر لتاجر مختلف يرجع 403 دون كشف وجوده.

## إنشاء الصنف

POST /api/v1/items

```json
{
  "merchantId": "UUID_FROM_MERCHANT_API",
  "name": "قميص",
  "brand": "Acme",
  "color": "أزرق",
  "weightKg": "0.250",
  "notes": "ملاحظات تعريفية اختيارية"
}
```

استبدل merchantId بهوية UUID فعلية من واجهة التجار. الحقول merchantId وname وbrand وcolor وweightKg مطلوبة. يمكن إرسال null للماركة أو اللون عند عدم انطباقهما؛ الملاحظات اختيارية ويمكن مسحها بـnull. النصوص تُزال فراغاتها الطرفية ويُرفض الفارغ.

الوزن بالكيلوجرام، نص عشري موجب بحد أقصى تسع خانات صحيحة وثلاث عشرية. أمثلة صحيحة: "0.001" و"1" و"1.125"؛ الاستجابة تعرض دائمًا ثلاث خانات مثل "1.000". لا أرقام JSON أو صيغة علمية أو أصفار بادئة أو تقريب تلقائي. مجال الوزن 0.001–999999999.999.

الاسم حتى 200 حرف، الماركة واللون حتى 100 حرف، والملاحظات حتى 2000 حرف. أي حقل إضافي مثل balance أو code أو ordinal أو createdById أو createdAt يُرفض.

نجاح الإنشاء 201، والصنف يرجع بالحقول: id، merchantId، code، name، brand، color، weightKg، notes، isActive، createdById، createdAt، updatedAt. لا ordinal أو بيانات الحساب السرية أو رصيد مختلق. المنشئ من الجلسة ووقت الإنشاء من القاعدة.

## القراءة والبحث

- GET /api/v1/items: قائمة وصفحات، items وtotal وpage وlimit.
- GET /api/v1/items/:id: تفاصيل UUID صالح.
- GET /api/v1/items/by-code/:code: بحث مطابق للكود؛ يحوّل الحروف إلى uppercase ويزيل الفراغات الطرفية وعلامة نهاية القراءة CR/LF.

فلاتر القائمة: merchantId، isActive=true أو false، search في الكود والاسم والماركة واللون، page من 1 حتى 1000000، limit افتراضيًا 25 وبحد أقصى 100. الترتيب createdAt ثم id تنازليًا؛ العدد والصفحة من نفس snapshot. التصفح ليس snapshot محفوظًا بين طلبات منفصلة عند وصول بيانات جديدة.

الافتراضي يعرض النشط والمعطل معًا حتى يبقى التاريخ متاحًا؛ استخدم isActive=true لاختيار النشط. حساب التاجر يستطيع رؤية أصنافه المعطلة أيضًا ما دام الحساب والتاجر نشطين. فلاتر غير معروفة أو غير صالحة ترجع 400.

## بيانات ملصق الباركود

GET /api/v1/items/:id/label

```json
{
  "code": "MZ-000001",
  "symbology": "CODE128",
  "itemName": "قميص",
  "merchantName": "شركة محمد زيدان",
  "merchantCode": "MZ"
}
```

هذه بيانات الملصق، وليست صورة أو PDF أو أمر طباعة. تكرار الطلب لا يضيف صنفًا ولا يخصص كودًا جديدًا. توليد الملصق بصريًا والطباعة واختبار الجهاز والقارئ الفعلي مرحلة مستقلة لاحقة. البحث بالكود جاهز لعميل يرسل القيمة التي قرأها الجهاز.

## تعديل البيانات والتعطيل

PATCH /api/v1/items/:id للمدير: name وbrand وcolor وweightKg وnotes، وحقل عمل واحد على الأقل، مع reason إلزامي بين10 و2000 حرف بعد trim. null مسموح فقط للماركة واللون والملاحظات. الكود والتاجر والمنشئ ووقت الإنشاء ثابتة حتى على مستوى SQL.

PATCH /api/v1/items/:id/status للمدير:

```json
{"isActive": false, "reason": "تعطيل الصنف بناءً على قرار المدير"}
```

التعطيل يحفظ السجل والكود، والتفعيل يستخدم الكود نفسه. لا DELETE endpoint. يمكن للمدير تصحيح وصف صنف تابع لتاجر معطل؛ إضافة صنف جديد لذلك التاجر ممنوعة. تعطيل الصنف لا يغير أي رصيد؛ قواعد الصرف ستُنفذ في مرحلة المخزون.

## المعاملات والتزامن

الإنشاء: قفل حساب الكاتب → إعادة التحقق من الجلسة والدور وتغيير كلمة المرور → قفل FOR SHARE للتاجر → التأكد من نشاطه → زيادة ذرية للعداد → إنشاء الصنف → commit.

مراجعة الدور داخل المعاملة تمنع تنفيذ طلب قديم إذا تغيّر دور المستخدم أو تعطّل أو أُبطلت الجلسة وهو ينتظر. القفل المشترك يمنع تعطيل التاجر حتى تنتهي الكتابة الجارية، والكاتب الذي ينتظر تعطيله يقرأ الحالة الجديدة ويرفض الإنشاء. الكتابات الإدارية تستخدم AdminMutationService الموجود مع إعادة فحص المدير قبل تعديل الصنف.

تخصيص الكود يستخدم INSERT ON CONFLICT UPDATE في PostgreSQL داخل المعاملة نفسها. كل تاجر له عداد منفصل، والطلب الفاشل لا يحفظ صنفًا أو زيادة جزئية. الأرقام المحفوظة لا يعاد استخدامها عبر API. الحد الأقصى BigInt 9223372036854775807؛ تجاوزه يرجع 409 دون تدوير.

قواعد SQL تمنع تغيير هوية الصنف والمالك والكود والرقم والمنشئ ووقت الإنشاء، وتفرض تطابق الكود مع رمز التاجر والرقم عند الإدخال. توجد FK Restrict وUnique وقيود الوزن والأسماء. أدوات الإدارة المباشرة لقاعدة البيانات ليست واجهة المستخدم، وتتطلب صيانة مسؤولة؛ أنواع Decimal في PostgreSQL قد تقرّب مدخل SQL زائد الدقة، بينما API يرفضه قبل التخزين.

## التالف والملاحظات

الملاحظات هنا تعريفية للصنف. وصف خدش أو كسر في كمية واردة أو مرتجع يُسجل على عملية الاستلام والفحص نفسها، بكمية الضرر ووصفه الدقيق، لأن دفعات الصنف قد تختلف. لا تُعامل حالة الصنف العامة كبديل لفحص كل دفعة.

الاستلام وحالات المرتجعات واعتماد البضاعة ذات الملاحظات وحركات الرصيد ليست منفذة بهذه المرحلة. مخططها سيحافظ على استلام البضاعة وتوثيق الضرر دون إضافة مرتجع ذي ملاحظات للمتاح قبل الاعتماد. لا يوجد رصيد تالف مستقل في المرحلة الأولى.

## نتائج التحقق

- build وlint: نجاح دون أخطاء أو تحذيرات lint.
- test:e2e: 78 اختبارًا ناجحًا، منها 28 للأصناف و50 للمصادقة والإدارة السابقة.
- test:db: 53 نتيجة ناجحة تشمل اختباري المجموعتين؛ 24 سيناريو جديدًا للأصناف.
- npm test: أربعة اختبارات كلمة مرور ناجحة.
- اختبارات فعلية لعشرين كاتبًا متزامنًا للتاجر نفسه، توسعة الكود بعد 999999، وتراجع المعاملة وحد العداد.
- اختبارات انتظار القفل مع تعطيل الكاتب وإبطال جلسته وتغيير الدور وفرض تغيير كلمة المرور وتعطيل التاجر.
- Prisma validate وmigrate status وmigrate diff: نجاح؛ لا فرق بين القاعدة والشيما بعد تطبيق الترحيل المحلي.
- مراجعة مستقلة داخلية للخدمات والأقفال والقيود والاختبارات: لا ملاحظات مؤثرة.

قواعد الاختبار منفصلة وتُحذف بعد التنفيذ. التطبيق المحلي يحتفظ ببياناته؛ الترحيل لم يضف أصنافًا تجريبية أو يغير حسابات التشغيل. تحذير Vite السابق حول vite-tsconfig-paths ما زال رسالة أدوات غير مانعة؛ لا تغيير للاعتماديات هنا.

### حالة حروف UUID في نطاق القراءة

فلتر `merchantId` الصحيح يقبل الحروف الصغيرة والكبيرة والمختلطة للهوية نفسها.
الخدمة تطبع الفلتر قبل مقارنة ملكية التاجر؛ هوية تاجر آخر تظل403، والتفاصيل
الأجنبية تظل404. غياب الفلتر يبقي نطاق جلسة التاجر؛ الأدوار الداخلية تحتفظ
بصلاحية القراءة عبر التجار. UUID غير صالح أو فلتر متعدد القيم يرجع400.
