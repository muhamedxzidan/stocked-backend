# بلوبرنت تنفيذ المصادقة والصلاحيات — Stocked Backend

**الحالة: اعتمد المستخدم التنفيذ؛ نفذت شريحة المصادقة الأساسية محليًا. نتائج التحقق وحدود الإنتاج في auth-api.md.**
**النطاق: /Users/mohamedzidan/project/stocked-backend فقط.**
لا تعديل في Flutter أو Firebase، ولا ترحيل بيانات سابقة، ولا نشر على سيرفر في هذه المرحلة.

## 1. الهدف والحدود
تحويل أساس الهوية الموجود إلى API دخول آمن قابل للصيانة، ثم البناء عليه في مراحل مستقلة.
هذه المرحلة تنفذ: اتصال قاعدة البيانات، تهيئة أول مدير، الدخول والخروج، الحساب الحالي، تغيير كلمة المرور، فحص الجلسات، وأساسي الصلاحيات والتوثيق والاختبارات.
إنشاء حسابات الفريق والتجار وإدارتها، استعادة كلمة المرور، والمخزون والشحن والمرتجعات مراحل تالية موثقة أدناه؛ لا تعتبر مكتملة بمجرد اكتمال الدخول.

## 2. الوضع الحالي ومسار التنفيذ
التطبيق الحالي: main.ts → AppModule → AppController → AppService.
Prisma يعرف User وMerchant وSession؛ الترحيل الأول موجود.
لا توجد خدمة مصادقة أو حراسة HTTP حاليًا. وجود الجداول لا يفرض صلاحيات الطلبات.
مسار التنفيذ المقترح:
HTTP → Validation → SessionGuard → PasswordChangeGuard → RolesGuard → Controller → Service → Prisma → PostgreSQL.
مسار الدخول العام يستثنى صراحة من حارس الجلسة ويخضع لتحديد المحاولات والتحقق من كلمة المرور.
التهيئة الأولى مسار CLI مستقل يستخدم خدمة التهيئة؛ لا endpoint عام لإنشاء مدير.

## 3. توزيع المسؤوليات والملفات
تضاف الملفات التي لها مسؤولية فعلية فقط، ولا تنشأ طبقات شكلية.

Controllers تتعامل مع HTTP فقط؛ قواعد الأمان في الخدمات؛ اتصال قاعدة البيانات في PrismaService.
لا إضافة Repository عام يكرر Prisma. يمكن استخراج استعلامات ميزة بعينها لاحقًا عند وجود حاجة فعلية.

## 4. الحزم المقترحة ولماذا
- argon2: تجزئة Argon2id والتحقق؛ crypto SHA-256 مخصص لتجزئة رموز الجلسات وليس كلمات المرور.
- class-validator وclass-transformer: DTO validation في Nest ورفض الحقول غير المسموحة.
- @nestjs/swagger: عقد OpenAPI قابل للتجربة، مع حمايته أو تعطيله في الإنتاج.
- helmet: ترويسات HTTP الأمنية.
- نستخدم dotenv الموجود وcrypto المدمج، ولا نضيف JWT أو Redis في هذه المرحلة.
تثبت إصدارات متوافقة مع Nest 12 وESM/TypeScript الحاليين بعد فحص peer dependencies.
لا استخدام npm audit fix --force. الثغرات الحالية ليست محلولة: يفحص مسار كل اعتماد، ويزال الاعتماد غير المستخدم أو يحدث بصورة متوافقة؛ لا تغيير رئيسي غير معتمد.
إذا احتاج الحل تغيير Prisma الرئيسي أو آلية المصادقة يتوقف التنفيذ لعرض تعديل محدد للبلوبرنت.

## 5. كلمات المرور والتهيئة الأولى
- البريد lowercase مع trim؛ كلمة المرور نفسها لا trim ولا اقتطاع.
- طول 15–128 Unicode code points؛ حد حجم HTTP مستقل لمنع الطلبات الضخمة.
- Argon2id: memoryCost=19456 KiB، timeCost=2، parallelism=1 كبداية، مع قياس الأداء.
- منع كلمات المرور الشائعة وفق قائمة محلية موثقة المصدر والترخيص والتحديث. اعتماد القائمة شرط قبل تنفيذ هذه الجزئية؛ لا ادعاء اكتشاف كل كلمة مرور مسربة.
- لا خدمة خارجية لفحص كلمات المرور دون قرار واضح بشأن الخصوصية والتوافر.
- فشل عام موحد للحساب غير الموجود أو المعطل أو كلمة المرور الخاطئة؛ dummy hash عند عدم وجود البريد.
- CLI أول مدير يطلب كلمة المرور بإدخال مخفي وتأكيدها، ولا يقبلها في وسائط الأمر أو يسجلها.
- تهيئة أول مدير داخل transaction مع advisory lock مشترك؛ ترفض إذا وجدت أي حسابات. لا seed تلقائي عند التشغيل.
- المدير يبدأ mustChangePassword=true؛ حسابات الاختبار تنشأ في قاعدة اختبار فقط.

## 6. الجلسة وطريقة نقلها
- رمز عشوائي 32 بايت؛ تعاد قيمته مرة واحدة بعد الدخول، ويحفظ SHA-256 فقط.
- انتهاء مطلق 12 ساعة، وخمول 30 دقيقة. تحديث lastSeenAt لا يمد expiresAt.
- فحص الحساب والدور الحاليين والتاجر الفعّال في كل طلب؛ لا حفظ role أو merchantId من العميل أو نسخها داخل token.
- هذه الشريحة توفر Authorization: Bearer للـAPI والعميل الأصلي المستقبلي؛ لا دمج Flutter الآن.
- وصول متصفح بوساطة Cookies له شريحة مستقلة قبل ربط أي واجهة ويب: HttpOnly/Secure/SameSite، CSRF، CORS محدد، واختبارات المتصفح.
- لا تقديم Bearer المخزن في localStorage كحل أمان للويب، ولا اعتبار شريحة Cookies مكتملة الآن.
- تغيير كلمة المرور يتحقق من الحالية، يبطل جميع جلسات الحساب ويصدر جلسة جديدة؛ المعاملة تمنع اعتماد جزء فقط من العملية.
- mustChangePassword يسمح فقط بـ me وتغيير كلمة المرور والخروج؛ me يعرض الحالة اللازمة دون بيانات أعمال.
- logout يبطل الجلسة الحالية في الخادم. لا ثقة بحذف الرمز عند العميل وحده.
- لا تضمين token أو passwordHash أو tokenHash في logs أو URLs أو بيانات الحساب.

## 7. محاولات الدخول
يلزم تحديد محاولات يعمل عند تشغيل أكثر من نسخة؛ مخزن الذاكرة وحده غير كاف للنشر.
المقترح: جدول LoginAttemptBucket جديد في migration منفصلة، دون تعديل migration القديمة:
keyDigest فريد، windowStartedAt، expiresAt، attemptCount غير سالب.
المفتاح HMAC لمعرف البريد أو IP باستخدام سر منفصل؛ لا تخزين البريد الخام أو IP داخل مفاتيح الجدول.
بداية قابلة للضبط: 5 محاولات للحساب و20 للمصدر خلال 15 دقيقة؛ العد قبل التحقق وبشكل ذري تحت التزامن.
عند بلوغ الحد تعاد 429 مع Retry-After دون كشف وجود الحساب؛ لا قفل دائم.
التأخير المتدرج محدود، ولا يحتفظ باتصال DB أو transaction مفتوحة أثناء الانتظار.
تنظيف السجلات المنتهية بأمر صيانة موثق؛ انتهاء النافذة لا يعتمد على نجاح التنظيف.
عنوان المصدر يستخرج وفق proxy موثوق محدد؛ لا قبول X-Forwarded-For اعتباطًا.
هذه إضافة مقترحة للشيما تتطلب اعتماد البلوبرنت وليست جدولًا تم إنشاؤه.

## 8. الصلاحيات والعزل
- حماية endpoints افتراضيًا، وإعلان العامة صراحة.
- RolesGuard يأخذ الدور من الهوية الموثوقة فقط.
- merchantId مستمد من الحساب، ولا يعد تمريره في query أو body تفويضًا.
- دور MERCHANT للقراءة فقط في وظائف الأعمال القادمة.
- عزل بيانات التجار ينفذ داخل استعلامات ميزة المخزون والشحن، واختبارات ملكية السجلات؛ حارس الدور وحده لا يكفي.
- لا تضمين قواعد إبطال الحساب وتغيير الدور وآخر مدير في هذه الشريحة ما دامت endpoints الإدارة لم تنفذ؛ تنفذ وتختبر معها في المرحلة التالية.
- كل حركة أعمال مستقبلية تحصل على actorId ووقت الخادم من السياق الموثوق.

## 9. عقد API المقترح
| الطريقة والمسار | السلوك |
|---|---|
| POST /api/v1/auth/login | email وpassword؛ session token والانتهاء وحقول الحساب الآمنة |
| GET /api/v1/auth/me | الحساب الحالي ودوره وmerchantId وحالة تغيير كلمة المرور |
| POST /api/v1/auth/change-password | currentPassword وnewPassword؛ تدوير الجلسة وإبطال القديمة |
| POST /api/v1/auth/logout | إبطال الجلسة الحالية |

الأخطاء: 400 لمدخل غير صالح، 401 لدخول/جلسة غير صالحة، 403 لمنع صلاحية، 429 لحد المحاولات.
لا يخرج stack trace أو تفاصيل قاعدة البيانات في استجابة الإنتاج.
الخدمة لا تعلن نجاح الجاهزية إذا تعذر اتصال DB. السياسة الدقيقة للـhealth تكتب في عقد التشغيل.

3. إعداد البيئة واتصال Prisma والتحقق من بدء وإيقاف التطبيق.
4. ترحيل جدول محاولات الدخول واختبار قيوده والتزامن.
5. خدمة كلمة المرور وخدمة الجلسات.

8. التوثيق وسياسة logs وترويسات HTTP.
9. اختبارات unit وAPI على قاعدة اختبار مستقلة ذات اسم محمي؛ لا fixtures في stocked_dev.

11. مراجعة أمنية مستقلة للملفات المصرح بها فقط إن أجريت؛ لا مشاركة .env أو أسرار أو منح وصول للمشروع كاملًا.
12. تقرير ما نفذ والقيود المتبقية. النشر والإنتاج مرحلة منفصلة.

## 11. حالات الاختبار المطلوبة
- نجاح الدخول؛ نفس خطأ الفشل لبريد مجهول وحساب معطل وكلمة خاطئة.
- لا passwordHash/tokenHash في أي استجابة؛ لا tokens في السجل.
- الرمز الصحيح يعمل، المزور يفشل، المبطل والمنتهي والخامل يفشلون.
- تعطيل الحساب أو التاجر في DB يمنع جلسة قائمة؛ اختبار تغير الدور دون إعادة دخول.
- forced change يمنع الأعمال؛ تغيير ناجح يدور الرمز ويمنع كل الجلسات السابقة.
- تغيير كلمة المرور متزامن لا يترك جلسات قديمة صالحة أو يحدث نجاحًا جزئيًا.
- bootstrap مرتين أو متزامنًا ينشئ مديرًا واحدًا فقط.
- تحديد المحاولات ذري ومشترك بين مثيلين؛ النافذة المنتهية تعمل دون حذف السجل.
- DTO يرفض role وmerchantId والحقول الزائدة في مدخل الدخول.
- الرجوع للترحيل الأول واختبارات الهوية القائمة دون تراجع.
اختبارات ملكية مخزون التجار وآخر مدير وCSRF تأتي عند تنفيذ ميزاتها، ولا يدعى نجاحها الآن.

## 12. مراحل استكمال الباك اند
1. إدارة الحسابات والتجار: المدير فقط، ثبات رمز التاجر، التعطيل، الإبطال، آخر مدير، إعادة التعيين.
2. الأصناف والباركود: SKU منفصل لكل تاجر وتسلسل آمن تحت التزامن والطباعة.
3. الاستلام: كميات وحالة وملاحظات دقيقة؛ بدء الأرصدة بأول استلام فعلي.
4. التجهيز والخروج: لا حجز في المرحلة الأولى، منع الرصيد السالب والمعالجة الذرية ومنع تكرار الطلب، شركة شحن وتتبع.
5. المرتجعات: مطابق يضاف مرة واحدة؛ به كسر/خدش/تلف يستلم بملاحظات دقيقة ويبقى بانتظار اعتماد؛ تحديد مصير غير الصالح قبل تنفيذه.
6. دفتر الحركات: سجلات لا تعدل ولا تحذف، وتصحيح بتسويات بسبب وفاعل ووقت.
7. الجرد وقفل الحركات والتسوية بعد الاعتماد.
8. API التاجر للقراءة فقط مع اختبار عزل السجلات والفلاتر.
9. إعداد الإنتاج: migrations منفصلة عن DB runtime، TLS وأسرار ونسخ احتياطي واستعادة ومراقبة وفحص الاعتماديات.
10. التكاملات المستقبلية بواجهات مستقلة وwebhooks موثوقة وidempotency، بعد اعتمادها؛ لا ضمن المرحلة الأولى.

كل مرحلة لها بلوبرنت واختبارات وعقد API قبل ربط Flutter.
لا تعني قابلية التوسع إنشاء جداول أو interfaces لكل فكرة مستقبلية الآن.

## متابعة التنفيذ

القائمة المحلية اختيرت من SecLists بترخيص MIT وبنسخة ثابتة ومصدر وSHA256 محفوظين مع الأصول. تمنع الكلمات الشائعة، ولا تدعي تغطية جميع كلمات المرور المسربة.
المراجعة الخارجية السابقة تخص ملفات أساس الهوية الأربعة فقط؛ لم ترسل ملفات المصادقة الجديدة أو .env إلى Antigravity ولم تمنح وصولًا أوسع.
تحقق من سجل التنفيذ في auth-api.md؛ خطة استكمال بقية الباك اند لم تنفذ ضمن هذه الشريحة.
