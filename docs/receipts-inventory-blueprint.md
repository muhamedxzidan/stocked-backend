# مخطط الاستلام وحركات الرصيد والتسويات

الحالة: معتمد ونُفذ في stocked-backend؛ سجل الفحوص ونتائج التشغيل في [دليل الاستلام](receipts-api.md) وملحق التنفيذ أدناه.
التاريخ: 9 أكتوبر 2026. المشروع: stocked-backend فقط.

## 1. الغرض والقرارات المثبتة

تنفيذ أول استلام فعلي من التاجر، وتسجيل حالته وبنوده والموظف ووقت الخادم، وزيادة الرصيد وسجل الحركات معًا. يبدأ النظام دون بيانات أعمال سابقة أو أرصدة افتتاحية. إنشاء الصنف وحده يظل دون كمية.

**قرار المستخدم الصريح في هذه المرحلة: كل الكمية المستلمة فعليًا من التاجر تدخل الرصيد، حتى المكسور والمخدوش أو التالف، مع توثيق الملاحظات بدقة.** لا يُعزل جزء من هذا الاستلام في رصيد تالف أو عهدة معلقة. المتاح في هذه النسخة هو الرصيد العام؛ ملاحظة العيب لا تمنع الصرف تلقائيًا. انتظار المراجعة يخص المرتجعات اللاحقة كما في الوثيقة الأصلية، وليس هذا الاستلام الأولي.

تشمل المرحلة الاستلام، قراءة الأرصدة والحركات، وتسوية تصحيحية موثقة للمدير أو أمين المخزن دون تعديل التاريخ. لا تشمل التجهيز والخروج وشركات الشحن والمرتجعات والجرد وحجز الأوردرات أو رصيدًا مستقلًا للتالف أو الصور أو Flutter.

قرارات هذا المخطط المقترحة للاعتماد: الكميات قطع صحيحة، حد البند 1,000,000 قطعة، حتى 100 بند للمستند ضمن سقف HTTP الحالي 16KiB، ومستودع تشغيل واحد MAIN مبدئيًا. الحد الأكبر لحجم الطلب يرجع 413 ولا يرفع سقف HTTP ضمنيًا. الرصيد Int من صفر حتى 2,147,483,647؛ الزيادة التي تتجاوز الحد تُرفض بدل التقريب أو overflow.

## 2. الوضع الحالي والمسار المتحقق منه

- Prisma schema الحالية: User وMerchant وSession وLoginAttemptBucket وItem وItemCodeSequence فقط؛ لا أرصدة أو مستندات استلام.
- ItemsService ينشئ الصنف داخل معاملة: قفل المستخدم، إعادة فحص الجلسة والدور، قفل التاجر FOR SHARE، ثم تخصيص الكود وإنشاء الصنف. تعديل بيانات الصنف للمدير يقفل الصنف بعد التاجر.
- SessionService يعيد قراءة المستخدم والجلسة والتاجر؛ دور أو حالة الحساب لا يعتمد على بيانات العميل.
- AdminMutationService يستخدم قفل إدارة مشتركًا ثم أقفال المستخدمين. تعطيل التاجر يقفل المدير وحسابات MERCHANT التابعة ثم يحدث التاجر. الموظف الداخلي لا يتبع merchantId بحسب قيد SQL الحالي.
- DTO وValidationPipe يرفضان الحقول غير المعروفة؛ القاعدة متاحة عبر PrismaService. لا نضيف Repository أو UseCase لمجرد تغيير أسماء الطبقات.
- لا خريطة Graphify للباك اند؛ فحص المصدر اقتصر على الخدمات والشيما والمستندات المتعلقة بهذه المرحلة. لم يُفحص أو يُعدل كود Flutter.

المسار الحالي: HTTP → حراس الجلسة وتغيير كلمة المرور والدور → DTO → Controller → Service → Prisma → PostgreSQL.
نقطة التغيير: إضافة مستندات الاستلام وسجل الرصيد وخدمات ترحيل الكميات داخل هذه الحدود الموجودة.

## 3. البيانات التي يكتبها الموظف

الطلب يحتوي التاجر وملاحظات المستند الاختيارية وبنود البضاعة المستلمة فعليًا. لا يقبل الرصيد الحالي أو النهائي أو هوية الموظف أو اسمه أو وقت العملية أو warehouseId من العميل في هذه النسخة.

كل بند يمثل كمية متجانسة الحالة:

| الحقل     | القاعدة                                                              |
| --------- | -------------------------------------------------------------------- |
| itemId    | UUID لصنف تابع لنفس التاجر                                           |
| quantity  | عدد صحيح موجب للقطع التي وصلت فعلًا                                  |
| condition | GOOD أو NOTED                                                        |
| issueType | null للسليم؛ BROKEN أو SCRATCH أو DAMAGED أو OTHER لذي الملاحظات     |
| notes     | null للسليم؛ وصف بعد إزالة الفراغات من 10 إلى 2000 حرف لذي الملاحظات |

اسم نوع العيب ليس وصفًا كافيًا وحده. الموظف يوضح الموضع والحالة وحجم الضرر، مثل «كسر في زاوية القاعدة مع شرخ بطول 3 سم». شرط طول الملاحظة يقلل الأوصاف الفارغة، لكنه لا يثبت صدق الفحص أو دقته؛ جودة الوصف مسؤولية الفاحص.

يمكن تكرار الصنف في المستند كمجموعات منفصلة لا تتداخل: 8 قطع GOOD، وقطعتان NOTED/SCRATCH، وقطعة NOTED/BROKEN. الزيادة 11 قطعة، وكل مجموعة تحتفظ بوصفها. إذا كانت قطعة بها كسر وخدش معًا تسجل مرة واحدة ضمن مجموعة وتوضح الحالتين في الوصف، فلا تُعد مرتين. لا نضيف كمية ناقصة لم تصل إلى المخزن؛ quantity هي الكمية الفعلية لا المتوقعة.

## 4. الجداول والعلاقات

### Warehouse

UUID وcode ثابت فريد وname وcreatedAt. يضيف الترحيل سجلًا مرجعيًا واحدًا MAIN للمخزن الرئيسي؛ لا يضيف أصنافًا أو حركات أو أرصدة أو حسابات. warehouseId يأتي من الخادم. وجود معرف حقيقي للمخزن يحفظ بعد المخزن داخل العلاقات منذ أول حركة، دون بناء إدارة عدة مخازن الآن.

### Receipt

UUID، warehouseId، merchantId، receivedById، receivedByNameSnapshot، receivedAt من القاعدة، notes اختيارية حتى 2000 حرف، idempotencyKey UUID، requestHash SHA-256 بصيغة 64 hex. فريد على warehouseId وidempotencyKey. لا بنود مسودة أو اعتماد منفصل في هذه المرحلة: إنشاء صحيح يعني استلامًا معتمدًا وزيادة رصيد في المعاملة نفسها.

وقت العملية وهوية واسم المستلم من الخادم بعد إعادة التحقق من الحساب. نسخة الاسم تحافظ على الاسم المسجل وقت العملية إذا عُدّل الحساب لاحقًا. اسم التاجر ورمز الصنف واسم الصنف وقت الاستلام يحفظان في snapshots اللازمة لثبات المستند وإعادة الطلب؛ لا تعتمد استجابة المستند على أسماء قابلة للتعديل بعد تسجيله.

### ReceiptLine

UUID، receiptId، position، warehouseId، merchantId، itemId، itemCodeSnapshot، itemNameSnapshot، quantity، condition، issueType، notes. position يبدأ من 1 وفريد داخل المستند. لا Unique على الصنف داخل الاستلام لأن حالاته قد تختلف بين المجموعات.

مفاتيح خارجية مركبة تربط البند بالمستند والمخزن والتاجر والصنف نفسه. يُضاف Unique على Item(id, merchantId) في الترحيل الجديد لفرض الملكية عبر SQL، دون تغيير مالك أي صنف أو تعديل ترحيل قديم.

### InventoryBalance

مفتاح مركب warehouseId وitemId؛ merchantId بعلاقة مركبة متطابقة مع الصنف؛ quantity Int غير سالب، وupdatedAt من الخادم. لا مدخل يدوي لهذا الجدول عبر API. لا ينشأ رصيد لمجرد إنشاء الصنف؛ قراءة صنف بلا حركة ترجع صفرًا منطقيًا.

هذا رصيد القراءة السريع، ومجموع StockMovement.quantityDelta هو سجل تغيراته القابل للمطابقة. التحديث والحركة والمستند دائمًا داخل معاملة واحدة، ولا يوجد عامل خلفي يضيف الرصيد لاحقًا.

### StockMovement

UUID، warehouseId، merchantId، itemId، kind، quantityDelta، actorId، actorNameSnapshot، recordedAt من القاعدة، receiptLineId أو adjustmentId. الأنواع الحالية فقط RECEIPT_IN وADJUSTMENT_IN وADJUSTMENT_OUT؛ لا أنواع شحن أو مرتجعات غير منفذة.

RECEIPT_IN قيمة موجبة وreceiptLineId موجود. نوع التسوية يحدد إشارة delta وله adjustmentId موجود. مصدر واحد فقط لكل حركة؛ كل receiptLineId أو adjustmentId يرحل مرة واحدة بقيد فريد. FK مركبة وقيود/Trigger عند الحاجة تمنع ربط الحركة بمالك أو مخزن أو صنف أو كمية تختلف عن مصدرها.

### StockAdjustment

مستند تصحيح لصنف واحد: UUID، warehouseId، merchantId، itemId، referenceMovementId، direction IN أو OUT، quantity موجبة، reason من 10 إلى 2000 حرف، performedById ونسخة الاسم ووقت الخادم، idempotencyKey وrequestHash.

المرجع حركة RECEIPT_IN موجودة بالفعل لنفس المخزن والتاجر والصنف. هذا يمنع إنشاء أرصدة افتتاحية عبر التسوية قبل أي استلام. لا تسوية جماعية أو بنود تسوية إضافية في هذه المرحلة؛ تصحيح صنف واحد لا يحتاج جدول بنود مستقلًا.

مثال: استلام سجل 10 بدل 8 → تسوية OUT بقطعتين وسبب ومرجع الحركة الأصلية. استلام سجل 8 بدل 10 → تسوية IN بقطعتين للمرجع نفسه. الأصل يظل كما سُجل، ويظهر التصحيح في الحركة الجديدة. التصحيح الجديد للتسوية نفسها يستمر في الإشارة للاستلام الأصلي مع سبب واضح؛ لا تعديل أو إخفاء للتسوية السابقة.

لا يسمح OUT برصيد سالب، ولا IN بتجاوز حد Int. تكرار تصحيحات منفصلة مشروع بمفاتيح وأسباب مستقلة؛ لا نضع حدًا مصطنعًا يجعل تصحيح كمية ناقصة مستحيلًا. قرار ومصداقية التسوية مسؤولية الأمين أو المدير.

### قيود SQL المشتركة

- FK Restrict؛ لا حذف متسلسل يمحو السجل.
- UPDATE وDELETE ممنوعان على Receipt وReceiptLine وStockMovement وStockAdjustment بقاعدة البيانات، وليس بإخفاء أزرار فقط.
- CHECK للكميات والحالة وحقول الملاحظات وإشارة الحركة وتنسيق hash وسبب التسوية.
- Unique لمصدر الحركة ونتيجة العملية؛ ownership composite keys تمنع خلط التجار حتى بالكتابة المباشرة الخاطئة.
- الفهارس تستهدف المخزن والتاجر والصنف والموظف والوقت وUUID لكسر تعادل التصفح.
- لا تُدّعى حماية السجل من مدير قاعدة يملك تعطيل Triggers أو تعديل DDL. صلاحيات حساب تشغيل القاعدة ومطابقة الرصيد والسجل جزء من تحضيرات الإنتاج، وليست ضمانًا ضد مالك القاعدة.

## 5. الصلاحيات والقراءة

| العملية                                    | المدير    | أمين المخزن | الموظف    | التاجر      |
| ------------------------------------------ | --------- | ----------- | --------- | ----------- |
| تسجيل استلام                               | نعم       | نعم         | نعم       | لا          |
| تسجيل تسوية تصحيحية                        | نعم       | نعم         | لا        | لا          |
| قراءة الاستلام والأرصدة والحركات والتسويات | كل التجار | كل التجار   | كل التجار | بياناته فقط |
| تعديل/حذف مستند أو حركة                    | لا        | لا          | لا        | لا          |

كل القراءة تقيد في SQL بـmerchantId من الجلسة عند دور MERCHANT، بما فيها التفاصيل وروابط المصدر والفلاتر. صنف أو مستند تاجر آخر يرجع 404؛ فلتر تاجر مختلف يرجع 403 دون كشف وجوده. عرض اسم المنفذ ووقته كما طلبت الوثيقة، دون البريد أو تجزئة كلمة المرور أو بيانات الجلسة أو requestHash.

قائمة الأرصدة تشمل أصناف التاجر حتى دون حركة وتعرض صفرًا، بما فيها المعطل للحفاظ على التاريخ؛ فلتر حالة الصنف متاح. الاستلام الجديد يتطلب تاجرًا وأصنافًا نشطة. التسوية تتطلب تاجرًا نشطًا، ويمكن تصحيح تاريخ صنف معطل دون إعادة تفعيله. هذه القاعدة المقترحة جزء من الاعتماد.

## 6. منع تكرار الطلب

Idempotency-Key UUID إلزامي في رأس كل POST للاستلام أو التسوية. يمثل عملية واحدة، ويجب الاحتفاظ به إذا فشل الاتصال أو تأخر الرد. لا توليد مفتاح جديد تلقائيًا لإعادة العملية نفسها.

المفتاح فريد داخل نوع العملية والمخزن، ومربوط بمنشئها. قبل حساب SHA-256 يبني الخادم كائنًا جديدًا من الحقول المسموحة فقط، بترتيب مفاتيح ثابت، ثم يستخدم JSON.stringify وUTF-8. لا يعتمد على ترتيب مفاتيح JSON الذي أرسله العميل.

عقد التطبيع المحدد:

- UUID، بما فيها المفتاح ومعرفات التاجر والصنف والمرجع، تُحفظ lowercase. quantity تتحقق كعدد صحيح وتُكتب كرقم في الكائن canonical.
- نصوص notes وreason تُزال فراغاتها الطرفية عبر DTO؛ الفراغات الداخلية والأحرف محفوظة دون تغيير Unicode أو اختصار الوصف.
- ملاحظات المستند الغائبة وnull تُكتب null. الحقول غير المطبقة على GOOD تكتب null بعد التحقق من عدم وجود ملاحظة أو نوع عيب متناقض.
- استلام: ترتيب الحقول operation، warehouseId من الخادم، merchantId، notes، lines. كل بند: itemId، quantity، condition، issueType، notes بالترتيب نفسه.
- تسوية: operation، warehouseId من الخادم، referenceMovementId، direction، quantity، reason. لا تدخل أسماء أو حالات الأصناف والتجار الحية في hash.
- ترتيب lines جزء من المستند ويبقى كما أرسله العميل؛ لا يتم فرز مجموعات الحالة عند حساب hash. فرز أقفال itemId مستقل عنه.
- الاستجابة تعتمد على snapshots المحفوظة، لا على مدخلات إعادة الطلب أو بيانات أسماء معدلة لاحقًا.

توجد اختبارات لإعادة الطلب بتغيير ترتيب مفاتيح JSON، ونفس optional notes كغائب أو null، وحروف UUID الكبيرة، دون كتابة ثانية؛ تغيير ترتيب البنود أو كمية فعلية مع المفتاح نفسه يعتبر طلبًا مختلفًا.

- نفس المفتاح والمنشئ والمدخلات → نفس المستند المحفوظ دون حركة أو زيادة ثانية.
- نفس المفتاح مع مدخلات مختلفة أو منشئ مختلف → 409 ورسالة عامة دون تسريب نتيجة الطلب الآخر.
- قفل transaction advisory حسب العملية والمفتاح يمنع إنشاء نتيجتين مع الطلبات المتزامنة؛ Unique يبقى خط دفاع مستقلًا.
- تُراجع الجلسة الحالية والدور قبل إرجاع النتيجة؛ الحساب المبطل أو الذي فقد الصلاحية لا يستفيد من مفتاح قديم.
- بعد نجاح الاستلام، تعطيل التاجر أو الصنف لا يمحو نتيجته: يمكن لمنشئ مخول حاليًا استعادة المستند نفسه بالمفتاح دون كتابة جديدة.
- POST يرجع المستند الثابت ونتيجة تسجيله، دون رصيد حي يتغير بعده. الأرصدة تُقرأ من GET مستقل.
- لا تاريخ انتهاء يحذف مفاتيح هذه المستندات؛ تظل جزءًا من المستند غير القابل للتعديل.

لا جدول idempotency عام الآن؛ فعليًا نحتاج نتيجة ثابتة داخل Receipt وStockAdjustment فقط. إذا ظهرت عمليات لاحقة لها دورة نتيجة مختلفة يُصمم احتياجها عندها.

## 7. ترتيب الأقفال وسلامة المعاملة

الاستلام المقترح:

1. قفل العملية والمفتاح داخل المعاملة.
2. قفل المستخدم، ثم إعادة SessionService.validate وفحص الدور وتغيير كلمة المرور.
3. فحص نتيجة محفوظة للمفتاح؛ إرجاعها أو رفض الاختلاف دون ترحيل جديد.
4. قفل التاجر FOR SHARE والتأكد من نشاطه.
5. قفل كل الأصناف الفريدة FOR SHARE بترتيب UUID ثابت، والتحقق من المالك والحالة. تُؤخذ جميع أقفال الأصناف قبل أقفال الأرصدة.
6. التعامل مع مفاتيح الرصيد بترتيب warehouseId/itemId ثابت. لكل مفتاح، تنفيذ INSERT ... ON CONFLICT (warehouse_id, item_id) DO NOTHING لتهيئة صفر إن كان غير موجود، ثم SELECT ... FOR UPDATE لصفه، قبل الانتقال للمفتاح التالي. لا UPDATE إلى صفر عند conflict، ولا فحص وجود ثم INSERT، ولا اعتماد على upsert قد تحوله أداة ORM إلى استعلامين. طلبا أول استلام متزامنان ينتظر أحدهما إنشاء/قفل الآخر بدل خطأ Unique أو ضياع الزيادة.
7. حساب الزيادة المجمعة لكل صنف دون فقد مجموعات الحالة الأصلية، والتحقق من الحد قبل تحويل النتيجة إلى Int.
8. إعادة فحص الجلسة بعد انتظار أقفال المخزون لالتقاط انتهاء الجلسة أو الخمول أثناء الانتظار، ثم أخذ وقت قاعدة البيانات وحفظ المستند والبنود والحركات وتحديث الرصيد والنتيجة المحفوظة في المعاملة نفسها.
9. commit؛ أي خطأ يلغي الجميع.

التسوية تستخدم الترتيب نفسه للكاتب والتاجر والصنف والرصيد، وتفحص مرجع الاستلام والكمية والإشارة قبل الترحيل. لا قفل إدارة عام لكل استلام؛ الموظفون المخولون يمكنهم التعامل بالتوازي.

ثابت ترتيب الأقفال: الاستلام والتسويات لا يرفعان قفل Item من FOR SHARE إلى FOR UPDATE ولا يعدلان بيانات الصنف أو يحاولان أخذ قفل الإدارة العام بعد بدء أقفال المخزون. تعديل الصنف الإداري يحتفظ بمساره الحالي: قفل الإدارة → المستخدم → التاجر → الصنف. يُوثق هذا الثابت عند مواضع الأقفال في الكود الجديد، وتراجع أي وحدة لاحقة ضده، مع اختبار تزامن استلام وتعديل حالة صنف. لا تغير وظيفي مطلوب لخدمة الأصناف الحالية.

قفل التاجر يمنع تعطيله خلال الكتابة؛ الطلب الذي ينتظر تحديث التاجر يرى حالته الجديدة. قفل الصنف يمنع تعطيله أو تغيير وصفه أثناء أخذ snapshot. أقفال UUID الثابتة تمنع طلبين يعالجان الصنفين بترتيب معكوس من حجز الأرصدة بترتيب مختلف.

التعارضات المؤكدة التي ألغت المعاملة، مثل deadlock/serialization، يمكن إعادة محاولتها بحد ثلاث محاولات إجماليًا، مع إعادة التحقق من الجلسة والمفتاح في كل مرة. لا إعادة تلقائية لأخطاء الأعمال أو التحقق أو اتصال غامض قد يكون بعد commit. عند فشل الاتصال يستعيد العميل النتيجة بالمفتاح نفسه. تحديد خطأ Prisma/adapter الفعلي يُثبت باختبار، ولا يعاد كل خطأ P2010 عشوائيًا.

## 8. API المقترح

كل المسارات تحت /api/v1، وبـBearer session صالح وتغيير كلمة المرور مكتمل.

| المسار                     | العملية                                          |
| -------------------------- | ------------------------------------------------ |
| POST /receipts             | تسجيل استلام مرة واحدة؛ Idempotency-Key مطلوب    |
| GET /receipts              | قائمة الاستلام بفلاتر النطاق والتاريخ والمنفذ    |
| GET /receipts/:id          | مستند وبنود الحالة والمنفذ والوقت ومراجع الحركات |
| GET /balances              | قائمة أرصدة الأصناف في المخزن الحالي             |
| GET /balances/:itemId      | رصيد الصنف، أو صفر قبل أول حركة، وفق الملكية     |
| GET /movements             | السجل بفلتر التاجر والصنف والمنفذ والنوع والوقت  |
| GET /movements/:id         | حركة ومصدرها ضمن النطاق نفسه                     |
| POST /stock-adjustments    | تصحيح لصنف واحد؛ Idempotency-Key مطلوب           |
| GET /stock-adjustments     | قائمة التصحيحات والأسباب والمنفذ والوقت          |
| GET /stock-adjustments/:id | تفاصيل التصحيح ومرجعه                            |

الصفحة تبدأ من 1، والحد الافتراضي 25 والأقصى 100، والترتيب وقت ثم UUID تنازليًا. فلاتر تاريخ UTC كاملة وصريحة؛ from شامل وto غير شامل، وfrom قبل to. لا endpoints لتحميل سجل كامل دون صفحات.

POST /receipts body النموذجي:

```json
{
  "merchantId": "UUID_FROM_MERCHANT_API",
  "notes": "وصلت البضاعة من التاجر",
  "lines": [
    {
      "itemId": "UUID_FROM_ITEM_API",
      "quantity": 8,
      "condition": "GOOD",
      "issueType": null,
      "notes": null
    },
    {
      "itemId": "UUID_FROM_ITEM_API",
      "quantity": 2,
      "condition": "NOTED",
      "issueType": "SCRATCH",
      "notes": "خدش واضح في الغطاء الأمامي بطول 2 سم"
    }
  ]
}
```

المثال يضيف 10 قطع من الصنف نفسه. قيم UUID مكانية تستبدل بهويات حقيقية. الكميات أرقام JSON صحيحة، بخلاف weightKg النصي في دليل الأصناف. warehouseId والمنفذ والوقت والرصيد النهائي ليست مدخلات.

POST /stock-adjustments body النموذجي:

```json
{
  "referenceMovementId": "UUID_FROM_RECEIPT_MOVEMENT",
  "direction": "OUT",
  "quantity": 2,
  "reason": "تم تسجيل عشر قطع بالخطأ؛ الكمية المستلمة فعليًا ثماني قطع"
}
```

التاجر والصنف والمخزن يُستخرجون من حركة المصدر، فلا يرسلهم العميل لتغيير الملكية. الاستلام والتسوية الجديدة يرجعان 201؛ استعادة نتيجة ثابتة ترجع 200 مع توثيق صريح في Swagger. نقص الرصيد أو تجاوز حدّه أو اختلاف مفتاح العملية يرجع 409؛ التفاصيل خارج النطاق 404؛ المدخل غير الصحيح 400. إضافة error codes لهذه الحالات تتم بشكل محدود داخل أخطاء هذه الوحدة دون إعادة كتابة مرشح الأخطاء الحالي أو تسريب SQL.

## 9. المسؤوليات وخريطة الملفات

| المكوّن                 | المسؤولية ولماذا هنا                                                           |

فصل StockPostingService له حاجة حالية: الاستلام والتسويات كلاهما يرحل كمية، ولا يصح نسخ حساب الرصيد وأقفاله في خدمتين. StockMutationService يحافظ على نفس فحص الجلسة الحالي دون إقحام الموظف في AdminMutationService الذي يتطلب ADMIN. لا قواعد حساب في Controllers ولا حزم إضافية لمجرد التنظيم.

الملفات المستهدفة بعد الاعتماد:

- prisma/schema.prisma: الكيانات الستة والعلاقات والفهارس والأنواع الحالية فقط.
- prisma/migrations/<new>/migration.sql: ترحيل جديد، المرجع MAIN، القيود المركبة وحماية السجل؛ لا تعديل للترحيلات السابقة ولا مسح بيانات التطوير.
- src/receipts/: Module وController وService، وDTO مستقل لكل طلب واستجابة وملفات اختيار الحقول.
- src/inventory/: وحدة الخدمات المشتركة للكتابة والترحيل والقراءة، وControllers الأرصدة والحركات وDTO وملكية القراءة.
- src/stock-adjustments/: Module وController وService وDTO وحقول الاستجابة.
- src/app.module.ts: توصيل الوحدات فقط.
- test/receipts/ وtest/inventory/ وtest/stock-adjustments/: اختبارات API والتزامن والصلاحيات.
- test/database/: قيود الملكية وحماية التاريخ والإشارات ومطابقة الرصيد.
- docs/receipts-api.md وdocs/inventory-api.md: العقود والأمثلة ونتائج التشغيل بعد التنفيذ، وتحديث README ودليل تصميم القاعدة.

لا Widget Tree لأن المرحلة لا تتضمن واجهة، ولا تعديل لأي ملف Flutter أو Firebase.

## 11. شروط القبول والاختبارات المطلوبة

- إنشاء صنف بلا حركة يظهر رصيده صفرًا؛ لا أرصدة افتتاحية أو fixtures في قاعدة التشغيل.
- استلام مختلط يزيد كل الكمية حسب قرارك ويحفظ كل مجموعة وملاحظة، بنفس الموظف ووقت الخادم.
- موظف وأمين ومدير يسجلون استلامًا؛ التاجر لا يكتب؛ الموظف لا يسجل تسوية.
- الملكية مفروضة لكل بند ومصدر حركة بقاعدة البيانات؛ مستند تاجر لا يقبل صنف تاجر آخر.
- التاجر لا يرى رصيدًا أو مستندًا أو حركة أو تسوية أو رابط مصدر لتاجر آخر، حتى بمعرف صحيح أو فلتر مزور.
- إعادة طلب متسلسل أو متزامن بنفس المفتاح لا تضيف كمية ثانية؛ اختلاف الطلب أو المستخدم يرفض بأمان.
- فشل أي بند أو فقد صلاحية الكاتب أثناء الانتظار يراجع من داخل المعاملة ويلغي المستند والبنود والحركات وكل زيادات الرصيد.
- طلبا أول استلام لنفس الصنف ينشئان صف رصيد واحدًا ويحتفظان بالزيادتين؛ الطلبات المتزامنة للصنف نفسه لا تفقد زيادات؛ الطلبات ذات ترتيب البنود المعكوس تتبع ترتيب الأقفال نفسه.
- تزامن الاستلام وتعطيل الصنف أو التاجر يتبع الأقفال دون ترقية قفل الصنف؛ انتهاء الجلسة أثناء انتظار الرصيد يمنع الترحيل بعد انتهاء الانتظار.
- تعديل اسم الصنف أو التاجر أو الموظف لا يغير المستند السابق أو نتيجة إعادة الطلب.
- تعديل/حذف receipt أو line أو movement أو adjustment عبر SQL يرفض؛ القراءة السابقة سليمة.
- التسوية OUT لا تجعل الرصيد سالبًا، وIN لا تتجاوز Int؛ أول رصيد لا يأتي من تسوية بلا استلام.
- SUM(delta) يطابق الرصيد بعد الاستلام والتصحيحات والتزامن والتراجع؛ لا كتابة منفصلة للرصيد عبر API.
- لا إعادة محاولة لأخطاء التحقق أو الأخطاء الغامضة بعد commit؛ إعادة المفتاح تستعيد النتيجة بعد محاكاة فقد الرد.
- نجاح build وlint وPrisma validate/migrate diff واختبارات المرحلة والاختبارات السابقة، مع حذف قواعد الاختبار المؤقتة.

## 12. متطلب تتبع الاستلام والتجهيز والمرتجعات

حسب تأكيد المستخدم، أهم ما يجب أن يبقى ظاهرًا وقابلًا للتتبع هو: **من استلم، ومن جهّز، ومتى حصلت كل خطوة**. تسجيل الاستلام الأولي جزء من التنفيذ الحالي للمخطط؛ التجهيز والمرتجعات مراحل لاحقة، لكن تصميمها يجب أن يحفظ هذا السجل ولا يستبدله بحالة حالية قابلة للتعديل.

كل حدث يستعمل هوية حساب المنفذ من الجلسة، والاسم المحفوظ كما كان وقت الحدث، ووقتًا يحدده خادم قاعدة البيانات. يحفظ الحدث في سجل مستقل مرتبط بمستنده، ويُعرض في التفاصيل والخط الزمني مع التاريخ والوقت. لا يستقبل API هوية المنفذ أو الاسم أو الوقت من العميل، ولا يكفي حقل updatedAt أو حالة مثل «تم التجهيز» وحدها لإثبات من نفذ العمل.

| الخطوة                         | ما يثبت في سجل الحدث                                                                                | القاعدة                                                                                                                 |
| ------------------------------ | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| استلام أولي من التاجر          | مستند الاستلام وبنوده، الموظف المستلم، اسمه وقتها، ووقت الخادم                                      | يسجل مرة واحدة مع إدخال كل كمية فعلية للرصيد. ملاحظات كل مجموعة حالة تبقى مع بندها                                      |
| تجهيز شحنة                     | حدث تجهيز مستقل، من جهّز، اسمه وقتها، وقت التجهيز، ومستند الشحنة                                    | لا يكتب فوق الاستلام أو يغير هوية منفذه. التجهيز لا يخصم رصيدًا في نطاق المرحلة الأولى                                  |
| استلام مرتجع فعلي              | من تسلمه من شركة الشحن، اسمه وقتها، وقت الوصول للمخزن، الشحنة والتاجر والبنود                       | يوثق الاستلام فورًا حتى لو نتيجة الفحص بها ملاحظات أو لا تدخل الرصيد بعد                                                |
| فحص أو اعتماد مرتجع ذي ملاحظات | نتيجة الفحص وملاحظاتها، ثم قرار الاعتماد أو الرفض وكمية القرار وسببه، منفذ كل حدث واسمه ووقت الخادم | استقبال المرتجع ليس هو اعتماد صلاحيته. يسجل المستلم والمراجع ووقتهما منفصلين، ولا يمحو قرار لاحق بيانات الاستلام الأولى |

هوية المستلم وهوية أمين المخزن أو المدير الذي اعتمد الحالة حقلان/حدثان منفصلان، ويظهر كلاهما للتاجر وفريق المخزن ضمن حدود الصلاحية. لا يفترض التصميم أن المستلم والمراجع يجب أن يكونا شخصين مختلفين؛ الوثيقة تحدد الأدوار المخولة للاعتماد ولا تفرض قاعدة فصل الأشخاص. عدم وجود اعتماد بعد يعني «بانتظار التأكيد» لا أن الاستلام لم يحدث.

إعادة إرسال الطلب بنفس مفتاحه تعيد المستند أو الحدث الأصلي، ولا تضيف استلامًا أو خطوة تجهيز أو استلام مرتجع ثانية. كل انتقال لاحق له eventId ثابت واسم ووقت خادم. لا تسمح واجهة التاريخ بتعديل سجل الحدث؛ التصحيح حدث منفصل موثق بسبب، وفق صلاحية الدور.

### حدود المرحلة الحالية

هذه المرحلة تنفذ مستند الاستلام الأولي فقط، وبداخله المستلم والاسم والوقت كحقول ثابتة. نموذج حدث تجهيز الشحنة واستلام المرتجع وفحصه وقراره مدون هنا لحماية العقد المستقبلي، لكنه لا يضيف endpoints أو جداول شحن أو مرتجعات وهمية في ترحيل المخزون الحالي. قبل تنفيذ أي منهما، يجهز له مخطط API وجداول وأدوار مستقل بنفس قاعدة actor + الاسم snapshot + server timestamp، ويعرض للموافقة حسب بوابة المشروع.

## 12. التوسع والجرد لاحقًا

warehouseId مثبت منذ أول حركة لتسهيل إضافة مخازن أخرى بعقد معتمد لاحقًا. Warehouse MAIN ليس واجهة إدارة مخازن متعددة الآن. فصل ترحيل الكمية يجعل الشحن والمرتجعات لاحقًا يضيفان أنواعًا ومصادر حركة دون نقل لوجيك الرصيد إلى Controllers أو نسخ قواعده.

الجرد غير منفذ بهذه المرحلة. قبل تفعيله، تُضاف دورة الجرد وقفل دائم موثق وفحص بوابة الحركات داخل StockMutationService، مع قواعد الاستلام المعلق وفك القفل. لا نضيف أعمدة أو endpoints وهمية ولا ندّعي أن الاستلام محمي من جرد غير موجود بعد.

الترحيلات المستقبلية تبقى إضافية ومراجعة؛ لا ربط Flutter بشكل الجداول مباشرة. رصيد التالف المستقل أو تتبع كل قطعة أو صور الفحص يحتاج نطاقًا معتمدًا جديدًا، ولا يُضاف ضمنًا.

## 13. المراجع والتحقق من التصميم

- [خريطة المتطلبات الأصلية](../../stocked/docs/backend-roadmap.md)، أقسام الاستلام وسلامة الرصيد ونموذج البيانات؛ قرار المستخدم الحالي أكد دخول كل كمية الاستلام الأول للرصيد.
- [PostgreSQL 17: أقفال الصفوف والتعارضات](https://www.postgresql.org/docs/17/explicit-locking.html): استُخدم لتقييم FOR SHARE وترتيب الأقفال وتحريرها بانتهاء المعاملة. ترتيب هذا المخطط قرار تصميم، وليس توصية جاهزة من التوثيق.
- [Prisma: المعاملات](https://www.prisma.io/docs/orm/fundamentals/transactions): مرجع للتحديثات الذرية وإدارة تعارضات المعاملة وإعادة المحاولات المحدودة.
- [PostgreSQL 17: الأنواع الرقمية](https://www.postgresql.org/docs/17/datatype-numeric.html): مرجع حدود Int؛ سقف البند وعدد البنود قرارات تطبيق مقترحة للاعتماد.

مراجعة Antigravity المعمارية اكتملت باستخدام claude-opus-4-6-thinking المتاح فعليًا، بملخص فني فقط داخل مجلد مؤقت، دون مشاركة مصدر الباك اند أو أسراره. ليست مراجعة مصدر أو إثباتًا لاختبارات تشغيل. تمت المراجعة عبر [مهارة agy-delegate](../../../.agents/skills/agy-delegate/SKILL.md) في وضع قراءة فقط ودون تجاوز الصلاحيات.

تم التحقق من ملاحظاتها مقابل المصدر قبل التنفيذ:

1. ترتيب الأقفال متوافق اليوم مع إدارة الأصناف. قُبل توثيق منع ترقية قفل الصنف أو أخذ قفل الإدارة من داخل معاملة المخزون، وإضافة اختبار التزامن.
2. سباق أول إنشاء رصيد: المقترح كان يستخدم upsert بالفعل؛ قُبل التوضيح الصريح INSERT ON CONFLICT DO NOTHING مع قفل الصف بالترتيب الثابت. لم يُقبل تعميم إعادة المحاولة على أي Unique violation لأن بعض التعارضات أخطاء بيانات حقيقية.
3. hash الطلب: قُبل تثبيت ترتيب الحقول وUUID وnull والفراغات وحدود التطبيع واختبار إعادة الطلب بدل الاكتفاء بكلمة «تطبيع».

لم توصي المراجعة ببديل أبسط يحقق النطاق نفسه. وافق المستخدم على المخطط ثم طلب التنفيذ.

- تنفذ المسارات الحالية الاستلام والقراءة والتسوية؛ التجهيز والخروج وشركات الشحن والمرتجعات والجرد تبقى خارج التنفيذ الحالي كما هو محدد في النطاق.
- في كل استلام تحفظ هوية المستلم ونسخة اسمه ووقت قاعدة البيانات في المستند والحركات. وفي التسوية تحفظ هوية المنفذ ونسخة اسمه ووقت قاعدة البيانات في مستندها وحركتها.
- قرار المستخدم: كل الكمية المستلمة تدخل الرصيد العام حتى القطع المكسورة أو المخدوشة، مع توثيق ملاحظة تفصيلية؛ لا ينشأ رصيد تالف مستقل.
- اختبارات HTTP للاستلام والتاجر والحركة والتسوية والتزامن وإعادة الطلب وسجل غير قابل للتعديل محفوظة في test/receipts/receipts.e2e-spec.ts. آخر تشغيل: 85 اختبار HTTP، و4 اختبارات وحدة، و53 اختبار قاعدة بيانات؛ build وlint وPrisma validate نجحت.
- طُبق الترحيل على stocked_dev بعد التحقق من اتصال localhost واسم القاعدة. بقي المستخدم الإداري الواحد، وظلت التجار والجلسات والأصناف والعدادات والاستلامات والأرصدة والحركات صفرًا؛ MAIN واحد.
