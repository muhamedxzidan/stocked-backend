## 2. البيئة والتقسيم المعتمد

- NestJS وTypeScript، بنظام ESM.
- PostgreSQL 17 داخل Docker للتطوير، وPrisma 7 للأنواع والنماذج والترحيلات.
- قاعدة التطوير المحلية: `stocked_dev` على `127.0.0.1:5432`، والمخزن المرجعي الحالي `MAIN`.
- توثيق OpenAPI/Swagger في التطوير. لا خدمة Firebase في هذا الباك إند.
- الإعدادات السرية في `.env`، ولا تدخل Git. راجع `.env.example` للإعدادات المطلوبة دون استبدال ملفك الحالي.
- وجود `warehouseId` في العمليات يحفظ بُعد المخزن؛ التشغيل الحالي يعتمد `MAIN`، ولا توجد إدارة عدة مخازن مكتملة.

المسار العام:

```text
HTTP → Guards → DTO → Controller → Service
     → معاملة Prisma → قيود PostgreSQL → مستند/دفتر حركة/رصيد
```

| المكان | أين تُكتب المسؤولية؟ |
| --- | --- |
| `src/<feature>/*.controller.ts` | المسارات، أدوار HTTP، استدعاء الخدمة، كود الرد |
| `src/<feature>/dto/` | التحقق من المدخلات وعقد الطلب والرد وتوثيق الحقول |
| `src/<feature>/*.service.ts` | قواعد العملية، الملكية، ترتيب الخطوات والمعاملة |
| `src/auth/` | الدخول والجلسات والحراس وإعادة التفويض |
| `src/inventory/stock-mutation.service.ts` | معاملة عمليات المخزن، الأقفال، إعادة التفويض ومحاولات تعارض التراجع |
| `src/inventory/stock-posting.service.ts` | أقفال الأرصدة، حدود الكمية وتحديث إسقاط الرصيد |
| `src/database/` | اتصال Prisma ووقت قاعدة البيانات |
| `src/http/` | التحقق العام، حدود الجسم، الأخطاء، Swagger |
| `prisma/schema.prisma` | النماذج والأعمدة والعلاقات وأنواع Prisma |
| `prisma/migrations/` | SQL التاريخي، والقيود والفهارس والـtriggers التي لا يكفي تمثيلها في الشيما |
| `test/` | اختبارات الوحدة وAPI وقيود قاعدة البيانات |
| `docs/` | العقود والسياسات والمخططات وحالة التنفيذ |

تعليمات الدخول ليست أعمدة شيما فقط: الشيما تخزن الحساب والدور والجلسة وعلاقاتها؛ الخدمات والحراس يفرضون سياسة الدخول والصلاحيات، وSQL يحمي سلامة الملكية والسجل والكميات. إخفاء زر في الواجهة لا يحقق التفويض.

لا تعدل `src/generated/prisma` يدويًا. الأنواع تتولد من الشيما. لا نضيف Repository أوUseCase أوحزمًا لمجرد اتباع اسم معماري؛ الطبقة الجديدة تحتاج مسؤولية حقيقية. فصل الخدمات حسب العملية هو النمط الحالي.

## 3. ما تم تنفيذه بالتفصيل

### 3.1 الهوية والدخول والأمان

- حساب خاص لكل مستخدم، ودور من الأدوار الأربعة المتفق عليها، وربط حساب التاجر بتاجره.
- حفظ كلمة المرور كـArgon2id hash، وجلسات opaque لا يُحفظ منها إلا بصمة الرمز.
- API للدخول والخروج والحساب الحالي وتغيير كلمة المرور.
- فحص انتهاء الجلسة والخمول ونشاط الحساب والتاجر عند الاقتضاء، وفرض تغيير كلمة المرور عند الحاجة.
- حراس مصادقة ودور وكلمة مرور، ورفض الوصول غير المصرح به من الخادم.
- عدادات محاولات دخول مشتركة في PostgreSQL، وسجل أمني، وأداة تنظيف للعدادات المنتهية.
- أمر تفاعلي لتهيئة أول مدير، بلا كلمات مرور أو حسابات افتراضية، ولا يستعمل بعد وجود حسابات.
- إعادة فحص التفويض داخل المعاملات وبعد انتظار أقفال عمليات المخزن.

المراجع: [سياسة الأمان](auth-security-policy.md)، [عقد المصادقة والتشغيل](auth-api.md)، [مخطط المصادقة](auth-implementation-blueprint.md).

### 3.2 المستخدمون والتجار

- إدارة الحسابات والأدوار وحالة النشاط بواسطة المدير.
- حماية آخر مدير، وإبطال الجلسات ذريًا عند التغييرات الحساسة وفق العقد الحالي.
- إدارة اسم التاجر والهاتف وحالة النشاط، ورمز فريد ثابت بعد الإنشاء.
- تعطيل التاجر أو الحساب يحفظ التاريخ؛ لا حذف لسجلات التشغيل لإخفاء عمليات سابقة.
- حساب التاجر مقيد بملكيته ولا يحصل على صلاحيات فريق المخزن.

المراجع: [عقد الإدارة](admin-api.md)، [مخطط المستخدمين والتجار](users-merchants-blueprint.md).

### 3.3 الأصناف والباركود

- كل صنف يتبع تاجرًا إلزاميًا، مع حماية الملكية من الخادم وقاعدة البيانات.
- كود تلقائي من رمز التاجر وعداده المستقل، مثل `MZ-000001`، ثابت وفريد.
- تخصيص العداد ذريًا لمنع تكرار الأكواد تحت التزامن.
- بيانات الاسم والماركة واللون والوزن والملاحظات والنشاط، مع وزن Decimal وعقد واضح للتمثيل النصي.
- إنشاء صنف جديد **لا يضيف كمية**؛ الرصيد يزيد بعملية مخزون فعلية فقط.
- قراءة وفلترة وبيانات ملصق CODE128؛ الواجهة والطابعة وقارئ الباركود تحتاج ربطًا واختبارًا لاحقًا.
- المرتجع لا ينشئ صنفًا جديدًا ولا يستهلك رقمًا من تسلسل أكواد التاجر.

المراجع: [عقد الأصناف](items-api.md)، [مخطط الأصناف والباركود](items-barcode-blueprint.md).

### 3.4 الاستلام الأول والأرصدة والتسويات

- مستند استلام وبنود، مرتبطان بتاجر ومخزن وصنف صحيحين.
- كمية وحالة `GOOD` أو`NOTED`، ووصف العيب عند وجود ملاحظات، مثل الكسر والخدش والتلف.
- اسم وهوية المستلم ووقت قاعدة البيانات، محفوظة دون قبول فاعل أو وقت من العميل.
- **القرار المعتمد للاستلام الأول:** كل الكمية تدخل الرصيد، بما فيها ذات الملاحظات، مع توثيق دقيق. لا رصيد تالف مستقل حاليًا.
- دفتر حركات ثابت، وإسقاط رصيد لكل صنف/تاجر/مخزن، وقراءة معزولة للتاجر.
- المستند والحركة والرصيد يثبتون في معاملة واحدة؛ الفشل يتراجع بالجميع.
- قاعدة البيانات تمنع الرصيد السالب وتفرض تطابقه مع مجموع الحركات.
- التسويات اليدوية للمدير فقط منذ مرحلة الجرد، بسبب موثق وبمرجع حركة استلام أول؛ Controller والخدمة وSQL تمنع الأمين. لا تعديل أو حذف للحركة الأصلية.
- **التسوية اليدوية لا تصلح لتصحيح مرتجع خاطئ**. فروق الجرد لها الآن مصدر stocktakeLineId ومسار اعتماد المدير المتخصص؛ لا تزوير لمرجع استلام.

المراجع: [الاستلام والتسويات](receipts-api.md)، [الأرصدة والدفتر](inventory-api.md)، [مخطط الاستلام والمخزون](receipts-inventory-blueprint.md).

### 3.5 الشحنات: الطلب → التجهيز → الخروج

- تسجيل طلب ببنود تتبع التاجر، ورقم شحنة مستقل مثل `SH-000001`.
- تسجيل من أنشأ الطلب ووقت التسجيل، ومن جهزه ووقت التجهيز، ومن سلّمه ووقت الخروج.
- الخروج يسجل شركة الشحن ورقم التتبع، ويشترط التجهيز أولًا.
- التسجيل والتجهيز لا يغيران الرصيد ولا يحجزان كمية مسبقًا.
- الخروج الحالي **كامل لكل بنود الشحنة مرة واحدة**؛ ليس خروجًا جزئيًا أو عدة دفعات لشحنة واحدة.
- الخروج يخصم `SHIPMENT_OUT` ذريًا، ويرفض إذا تجاوزت الكميات الرصيد المتاح عند الخروج.
- الحالة مشتقة `REGISTERED / PREPARED / DISPATCHED`، مع خط زمني وفلترة وقراءة مقيدة بالتاجر.
- منع تسجيل مرحلة ثانية أو خصم مرتين، ومفاتيح إعادة طلب مرتبطة بالفعل والمدخلات والحساب.
- **التتبع الحالي داخل المخزن:** مراحل الطلب والتجهيز والخروج، وشركة الشحن ورقم التتبع. لا استقبال آلي لحالة شركة الشحن أو إثبات توصيل للعميل حتى الآن.

المراجع: [عقد الشحنات](shipments-api.md)، [مخطط الشحنات](shipments-blueprint.md).

### 3.6 المرتجعات: استلام → فحص → قرار

- خمسة جداول تفصل إثبات الوصول وبنوده عن الفحص ومجموعاته وقرار المراجعة.
- استلام مرتبط بتاجر وشحنة خرجت فعلًا وبنود الشحنة الأصلية؛ الصنف والمخزن والخروج مشتقة من المصدر.
- الاستلام الفعلي لا يزيد الرصيد. المستلم والفاحص والمعتمد لكل منهم هوية ونسخة اسم ووقت خادم مستقل.
- الفحص يغطي كل الكمية، ويمكن تقسيم الصنف: مثل 8 سليمة و2 مكسورة من أصل 10.
- السليم `GOOD` يزيد الرصيد عند الفحص. `NOTED` يبقى خارج المتاح حتى قرار المدير أو الأمين.
- أنواع الملاحظات: `BROKEN / SCRATCH / DAMAGED / MISMATCH / OTHER`؛ ملاحظات دقيقة 10–2000 حرف.
- قبول أو رفض مجموعة الملاحظات كاملة، مع سبب 10–2000 حرف. الموظف لا يعتمد.
- `MISMATCH` لا يقبل لصالح SKU المتوقع؛ الرفض فقط في العقد الحالي.
- الرفض يبقي عهدة موثقة خارج الرصيد؛ لا يعني إتلافها أو تسليمها للتاجر.
- الأصناف المعطلة يمكن استلامها وفحصها بملاحظات ورفضها، لكن إعادة الرصيد تتطلب نشاط الصنف.
- مرتجعات جزئية ومتعددة مسموحة، لكن مجموع **كل الاستلام الفعلي** لا يتجاوز كمية الخروج، ويحسب المعلق والمرفوض وغير المفحوص أيضًا.
- حتى 100 بند استلام و600 مجموعة فحص؛ تصنيف GOOD واحد وحتى خمسة أنواع ملاحظات لكل بند، دون تكرار نفس التصنيف.
- جسم POST الفحص فقط يقبل حتى 4MiB لمسار UUID الصحيح؛ بقية المسارات والطرق 16KiB.
- حالة المرتجع `RECEIVED / PENDING_REVIEW / RESOLVED`، مع كميات المستلم وغير المفحوص والمعاد للرصيد والمعلق والمرفوض منفصلة.
- حماية SQL ضد تبديل التاجر أو الشحنة أو بند المصدر، وتزوير الحركة أو تكرارها، ومجموع فحص غير صحيح، وإضافة بنود متأخرة.
- الكتابة ReadCommitted وقفل المصدر قبل جمع المرتجعات؛ القراءة RepeatableRead للقطة متسقة.
- لا إلغاء أو تعديل أو إعادة فحص أو قرار جزئي أو صور عيوب أو رصيد مستقل للتالف في هذه الدفعة.
- **حد معروف:** استلام مرتجع بكمية خاطئة يستهلك سقف الإرجاع حتى لو رُفض؛ تصحيحه يحتاج مسارًا مستقلًا مستقبلًا، ولا نعالجه بحذف التاريخ أو تسوية استلام أول.

المراجع: [عقد المرتجعات](returns-api.md)، [المخطط المعتمد](returns-blueprint.md).

### الجرد والمواقع — منفذ محليًا بعد اعتماد المستخدم

- الأنواع: شامل FULL، تاجر بكل أرففه MERCHANT، صف ROW، رف SHELF؛ التاجر يمكنه امتلاك عدة أرفف.

- إدخال مواقع الاستلام والخروج والتسويات ودخول المرتجعات ضمن المعاملات الحالية؛ الطلب الناجح يحتاج توزيعًا كاملًا صحيح الملكية.
- عهدة المرتجعات مستقلة عن المتاح، مع مواقع ونقل موثق ومصادر سحب عند الفحص/القبول. فروق عهدة الجرد تحفظ للمتابعة دون تسوية المتاح.
- المدير أو الأمين يفتح ويعد مع تسجيل الحضور والمدير الحاضر؛ الموظف والتاجر للقراءة حسب الصلاحية. الاعتماد والإلغاء للمدير وحده.
- كل تعديل تجاري/إداري يقف للجميع، بما فيهم المدير، من تثبيت الفتح إلى الاعتماد أو الإلغاء. القراءة وإجراءات الدخول وتغيير كلمة المرور الذاتية وحماية الجلسة تبقى متاحة.
- قفل معاملات مشترك/حصري قبل أقفال المستخدم والرصيد، وحالة دورة محفوظة في PostgreSQL؛ SQL يحمي الكتابات أيضًا. الطلبات المنتظرة لا تتجاوز فتح الجرد.
- العد صفر صريح، ومراجعات العد ثابتة، وأسباب الفروق والحضور والملاحظات وسجل الأحداث مرقمة بالفاعل ووقت قاعدة البيانات.
- اعتماد المدير يثبت تسويات AVAILABLE زيادة/نقصان بمصدر الجرد، ثم الحركات والأرصدة والإغلاق وفك القفل في معاملة واحدة. فرق صفر لا ينشئ حركة؛ صافي صفر بين رفّين يحتفظ بالتسويتين.
- الإلغاء بسبب موثق يحفظ تاريخ الجرد دون تغيير كمية. لا استئناف دورة ملغاة ولا فك تلقائي للقفل عند إعادة تشغيل التطبيق.

الترتيب الآمن المقترح لكل تغيير:

1. وصف حاجة العميل وحدودها وتحديد المصدر والملفات المتأثرة.
2. تصميم مع اعتماد واضح قبل التنفيذ غير البسيط، والحفاظ على مسؤولية كل خدمة.
3. ترحيل جديد متوافق قدر الإمكان مع النسخة الموجودة، ومراجعة القيود والفهارس والأقفال.
4. عند تغيير كاسر: إضافة الجديد أولًا ثم نقل البيانات/المستهلكين وفق خطة ثم إزالة القديم في مرحلة مستقلة؛ لا حذف عمود تستخدمه النسخة الحية مباشرة.
5. اختبار البيانات القديمة والمتزامنة والملكية، ثم staging ونسخة احتياطية وخطة رجوع.
6. تطبيق الترحيل وإصدار التطبيق بالترتيب المعتمد، ومراقبة التشغيل وتوثيق النتيجة.

لا تعدل حركة قديمة أو snapshot لإصلاح وضع حالي. التصحيح مستند وحركة جديدة بمصدر وسبب ومنفذ واضحين، أو مسار تصحيح خاص عندما يؤثر في سقف الكميات الفعلية مثل المرتجعات.
