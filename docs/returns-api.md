# المرتجعات — عقد API

كل المسارات تحت `/api/v1` وتتطلب `Authorization: Bearer <session-token>`.
الأفعال الثلاثة تتطلب `Idempotency-Key: UUID v4`؛ الجديد 201، إعادة نفس المدخلات بنفس الحساب 200، تغيير المدخلات أو الحساب 409. مفاتيح الإجراءات مستقلة. نتائج POST أحداث ثابتة؛ GET يعرض الحالة الحالية.

## 1. الاستلام الفعلي

`POST /returns` — المدير، أمين المخزن، الموظف.

```json
{
  "merchantId": "merchant-uuid",
  "shipmentId": "dispatched-shipment-uuid",
  "notes": "وصلت العبوة مفتوحة، يلزم فحص محتوياتها",
  "lines": [{ "shipmentLineId": "original-shipment-line-uuid", "quantity": 10 }]
}
```

الخادم يشتق الصنف والمخزن والخروج والنسخ النصية من الشحنة، ويحفظ `receivedById` و`receivedByNameSnapshot` و`receivedAt`. لا يتغير الرصيد. الرد يتضمن `id`, `merchantId`, `shipmentId`, `dispatchId`, `merchantNameSnapshot`, `shipmentCodeSnapshot`, حقول المستلم والوقت، الملاحظات، و`lines` مع UUID بند المرتجع وكود/اسم الصنف وكميته وموضعه.

التاجر إلزامي ونشط والشحنة خرجت فعلًا. كل بند يتبع الشحنة والتاجر نفسهما. 1–100 بند، كمية صحيحة 1–1,000,000، ولا تكرار لبند الشحنة. مجموع **كل** المرتجعات الفعلية السابقة والجديدة لا يتجاوز كمية الخروج، حتى المعلق أو المرفوض أو غير المفحوص. لا إنشاء صنف ولا تغيير تسلسل أكواده.

## 2. الفحص الكامل

`POST /returns/:receiptId/inspect` — المدير، أمين المخزن، الموظف.

```json
{
  "lines": [
    { "receiptLineId": "return-receipt-line-uuid", "quantity": 8, "condition": "GOOD" },
    {
      "receiptLineId": "return-receipt-line-uuid",
      "quantity": 2,
      "condition": "NOTED",
      "issueType": "BROKEN",
      "notes": "كسر في الركن الأيمن لقطعتين، والعبوة ممزقة عند نفس الموضع"
    }
  ]
}
```

فحص واحد يغطي **كل** بنود الاستلام. مجموع مجموعات كل بند يساوي كميته تمامًا. لكل بند GOOD واحد اختياري، وحتى خمس مجموعات NOTED مختلفة: `BROKEN`, `SCRATCH`, `DAMAGED`, `MISMATCH`, `OTHER`. لا تصنيف مكرر؛ تجمع الكمية وتكتب تفاصيل العيب. الحد 600 مجموعة. GOOD بلا ملاحظات أو نوع عيب؛ NOTED بملاحظات دقيقة 10–2000 حرف ونوع عيب إلزامي.

الرد: `id`, `receiptId`, `inspectedById`, `inspectedByNameSnapshot`, `inspectedAt` و`lines`، وكل مجموعة فيها `id`, `receiptLineId`, `itemId`, `position`, `quantity`, `condition`, `issueType`, `notes`.

GOOD يضيف `RETURN_IN` ورصيد نفس الصنف والتاجر مرة واحدة. NOTED يبقى خارج الرصيد. يمكن أن يكون الفحص كله NOTED. الصنف المعطل يمكن استلامه وفحصه NOTED؛ GOOD يتطلب إعادة تفعيله. لا تصنيف غير حقيقي للتحايل على التعطيل.

حد الجسم **4MiB لهذا POST ومسار UUID الصحيح فقط**؛ بقية المسارات والطرق 16KiB. الحد بالبايتات الفعلية، وقد يرفض JSON كثير المسافات أو escapes رغم صحة الحقول.

## 3. قرار المجموعة ذات الملاحظات

`POST /returns/inspection-lines/:groupId/review` — المدير أو أمين المخزن فقط.

```json
{
  "decision": "ACCEPT_TO_STOCK",
  "reason": "تمت مراجعة القطعتين والتأكد من صلاحيتهما للصرف مع توثيق العيب"
}
```

بديل القرار `REJECT_OUTSIDE_STOCK`. السبب إلزامي 10–2000 حرف. القرار يشمل المجموعة كلها، وثابت مرة واحدة. القبول يضيف الرصيد بحركة مرتبطة بالمجموعة والقرار؛ الرفض لا يضيف رصيدًا. `MISMATCH` يسمح بالرفض فقط، ولا يزيد رصيد SKU المتوقع. الرد: `id`, `inspectionLineId`, `decision`, `reason`, `reviewedById`, `reviewedByNameSnapshot`, `reviewedAt`.

رفض المجموعة لا يعني الإتلاف أو تسليمها للتاجر: تظل عهدة موثقة خارج الرصيد. الصنف المعطل يجوز رفضه، ولا يجوز قبوله إلى الرصيد.

## 4. القراءة والتتبع

`GET /returns` بفلاتر اختيارية: `merchantId`, `shipmentId`, `itemId`, `status`, `receiverId`, `inspectorId`, `reviewerId`, `from`, `to`, `page`, `limit`.

`from` شامل و`to` غير شامل لتاريخ الاستلام `receivedAt`. الصفحة 1 والحد 25، أقصى حد 100. الترتيب وقت الاستلام ثم UUID تنازليًا. الرد `{items,total,page,limit}`.

`GET /returns/:receiptId` يعرض الاستلام وبنوده والفحص ومجموعاته ومراجعاته و`timeline` مرتبًا: المستلم، الفاحص، ثم كل قرار ومعتمده. الأسماء المحفوظة لا تتغير بتعديل أسماء الحسابات. وقت كل حدث من الخادم ولا يقبله النظام من العميل.

حالة الاستلام مشتقة: `RECEIVED` قبل الفحص، `PENDING_REVIEW` إذا بقيت مجموعات دون قرار، `RESOLVED` بعد اكتمال الفحص والقرارات. حالة المجموعة: `GOOD_RESTOCKED`, `PENDING_REVIEW`, `ACCEPTED_TO_STOCK`, `REJECTED_OUTSIDE_STOCK`.

`quantities` يحتوي `received`, `uninspected`, `restocked`, `pending`, `rejected`. المستلم = غير المفحوص + المعاد للرصيد + المعلق + المرفوض. ليست هذه الحقول أرصدة مستقلة للتالف؛ الرصيد المتاح من دفتر المخزون.

كل الفريق يقرأ كل التجار. حساب التاجر يقرأ تاجره فقط: فلتر تاجر آخر 403، UUID مرتجع أو حركة لتاجر آخر 404، بقية الفلاتر تبقى داخل ملكيته. `GET /movements?kind=RETURN_IN` يعرض مصدر المرتجع ومن فحصه ومن اعتمده ومن استلمه والشحنة الأصلية.

## 5. ثبات السجل وحدود المرحلة

لا UPDATE أو DELETE أو إلغاء أو فحص ثانٍ أو قرار ثانٍ. قاعدة البيانات تفرض الملكية، سقف الكميات، مجموع الفحص، أصل حركة الرصيد وتطابق منفذها ووقتها وكميتها، وتطابق الرصيد مع SUM الدفتر عند commit. كل فعل ذري: فشل أي خطوة يتراجع بكل مستنداته وحركاته ورصيده.

الكتابة ReadCommitted مع قفل الشحنة قبل جمع الاستلام السابق؛ إدخال بنود استلام بغير هذا العزل يُرفض في SQL. القراءة RepeatableRead. الجلسة يعاد فحصها بعد انتظار الأقفال. لا مفاتيح إعادة أو hash أو أسرار في الردود.

تصحيح استلام مرتجع خاطئ، قبول جزء من مجموعة، صور العيوب، رصيد التالف، معالجة الصنف الفعلي المختلف، الإتلاف والتسليم والتكاملات ليست ضمن هذه الدفعة. الكمية المسجلة خطأ تستهلك سقف المرتجع حتى لو رُفضت؛ تحتاج مسار تصحيح مستقل لاحقًا. قاعدة إدخال كل الكمية مع الملاحظات تخص الاستلام الأول من التاجر، وليست المرتجعات.

## الأخطاء

400: مدخلات غير صالحة أو فحص ناقص/متكرر التصنيف أو قبول MISMATCH. 401: جلسة غير صالحة. 403: دور غير مسموح أو فلتر ملكية مختلف. 404: مصدر غير موجود/خارج ملكية التاجر. 409: تجاوز سقف المرتجع، تاجر/صنف غير متاح، مرحلة مكتملة بمفتاح جديد، أو تعارض مفتاح. 413: جسم الطلب يتجاوز الحد. خطأ التسجيل الداخلي يتراجع بالكامل ولا يعيد تفاصيل SQL أو أسرارًا.

## التحقق في هذه الدفعة — 9 أكتوبر 2026

- نجح البناء وPrisma validate وفحص الكود والأنواع والتنسيق.
- نجحت اختبارات API الشاملة: 126 اختبارًا؛ واختبارات SQL الشاملة: 126؛ والوحدة: 4. اختبارات المرتجعات تشمل 23 حالة API و46 حالة SQL بما فيها تجميع الاختبارات الفرعية.
- ثبت فحص 100 بند و600 مجموعة بملاحظات عربية طويلة، وحالات ملكية المصدر، والصلاحيات، وإعادة الطلب، والقرارات المتنافسة، والتراجع الكامل، وانتهاء الجلسة أثناء انتظار القفل، وثبات الأسماء، واتساق قراءة الحالات، وحدود أجسام الطلبات. اختبارا اتصال SQL متزامنين يثبتان السقف خارج API أيضًا.
- طبقت الترحيلات الثمانية على stocked_dev المحلية. المقارنة قبل/بعد أثبتت ثبات أعداد السجلات وكل صفوف الرصيد، دون بيانات تشغيل تجريبية أو reset.
- اكتمل التحقيق المصدري عبر Antigravity، وتحقق Codex من التنفيذ والقيود والاختبارات مباشرة. **المراجعة المستقلة النهائية لم تكتمل**: أعادت كل نماذج المراجعة المحددة خطأ نفاد الحصة 429؛ لم يعد تشغيلها أو يُدَّع نجاحها. هذه الدفعة لا تعني اعتماد نشر الإنتاج.

## امتداد المواقع والعهدة — 9 أكتوبر 2026

كل بند استلام مرتجع يحتاج placements لمواقع العهدة. GOOD بالفحص أو قبول NOTED يحتاج placements للمتاح، وcustodySources لتحديد أرفف سحب العهدة إذا اختلفت عن أرفف الإضافة. المعلق والمرفوض يحتفظان بالعهدة خارج الرصيد المتاح. جميع كتابات المرتجعات تتوقف أثناء الجرد. فروق عد العهدة توثق دون تسوية المتاح. راجع [عقد المواقع](storage-locations-api.md) و[عقد الجرد](stocktakes-api.md).
