# عقد الاستلام والتسويات

تسجيل الاستلام عملية واحدة ذرية: ينشئ النظام مستند الاستلام وبنوده وحركات `RECEIPT_IN` ويحدث الرصيد داخل معاملة PostgreSQL واحدة. يرجع أي فشل في بند أو قيد أو تحديث الرصيد كل ما سبق. الصنف الذي أُنشئ ولم يستلم بضاعة يظهر برصيد صفر.

كل الكمية التي وصلت فعليًا تدخل الرصيد العام، حتى المكسور أو المخدوش. يقسم الموظف الكمية إلى بنود متجانسة الحالة. `GOOD` لا يقبل نوع عيب أو ملاحظة. `NOTED` يحتاج نوعًا ووصفًا واضحًا من 10 إلى 2000 حرف، ويجب وصف مكان العيب وشدته؛ النوع وحده لا يكفي. تسجيل الملاحظة لا يعزل القطع عن الرصيد المتاح في هذه المرحلة.

## المسارات

| الطريقة والمسار                     | الصلاحية                              | النتيجة                                                  |
| ----------------------------------- | ------------------------------------- | -------------------------------------------------------- |
| `POST /api/v1/receipts`             | مدير النظام، أمين المخزن، موظف المخزن | استلام جديد `201`، أو نتيجة محفوظة `200` عند إعادة الطلب |
| `GET /api/v1/receipts`              | أدوار المخزن، والتاجر ضمن نطاقه       | قائمة مرقمة وبفلاتر التاجر والمنفذ والتاريخ              |
| `GET /api/v1/receipts/:id`          | أدوار المخزن، والتاجر المالك          | المستند وبنوده والمستلم ووقت الخادم                      |
| `POST /api/v1/stock-adjustments`    | مدير النظام فقط                      | تسوية موثقة `201` أو إعادة آمنة `200`                    |
| `GET /api/v1/stock-adjustments`     | أدوار المخزن، والتاجر ضمن نطاقه       | قائمة مرقمة بالتاجر والمنفذ والتاريخ                     |
| `GET /api/v1/stock-adjustments/:id` | أدوار المخزن، والتاجر المالك          | التسوية وسببها ومرجعها والمنفذ ووقت الخادم               |

يرسل طلب الاستلام `Idempotency-Key` كرأس UUID v4، وجسمًا مثل:

```json
{
  "merchantId": "UUID",
  "notes": "وصلت البضاعة من التاجر",
  "lines": [
    { "itemId": "UUID", "quantity": 8, "condition": "GOOD", "placements": [{"shelfId":"UUID","quantity":8}] },
    {
      "itemId": "UUID",
      "quantity": 2,
      "placements": [{"shelfId":"UUID","quantity":2}],
      "condition": "NOTED",
      "issueType": "SCRATCH",
      "notes": "خدش واضح في الغطاء الأمامي بطول 2 سم"
    }
  ]
}
```

يسمح من 1 إلى 100 بند، وكمية كل بند من 1 إلى 1,000,000 قطعة. يمكن للصنف أن يظهر في أكثر من بند إذا اختلفت الحالة. لا يقبل الخادم `warehouseId` أو الموظف أو الاسم أو الوقت أو الرصيد من الطلب. يسجل وقت قاعدة البيانات واسم الحساب الحالي وقت العملية، ويحتفظ بهما في المستند والحركة.

يعيد الخادم الطلب بنفس النتيجة إذا تطابق المفتاح والموظف ومحتوى الطلب المطبع. اختلاف المحتوى أو الموظف مع نفس المفتاح يرجع `409`، ولا يكرر الزيادة. يعاد فحص الحساب والجلسة والدور قبل إعادة النتيجة. يعالج التزامن بأقفال PostgreSQL مرتبة على التاجر والأصناف والأرصدة.

## التصحيح

التصحيح يخص صنفًا واحدًا، ويشير إلى حركة استلام أصلية للصنف نفسه. `direction` إما `IN` أو `OUT`، والكمية موجبة حتى 1,000,000، والسبب من 10 إلى 2,000 حرف. لا يسمح الرصيد السالب أو تجاوز الحد الأعلى لـ`INTEGER`. لا تعدل سجلات الاستلام أو التسوية أو الحركة ولا تحذف؛ يسجل أي تصحيح كحركة جديدة مع هوية المنفذ واسمه المحفوظ ووقت الخادم.

## المخرجات والسجلات

تفاصيل الاستلام تعرض `receivedById`, `receivedByNameSnapshot`, `receivedAt` وكل بند ومراجع حركاته. سجل الحركة يعرض `actorId`, `actorNameSnapshot`, `recordedAt`, `quantityDelta`, الصنف ونوع الحركة والمصدر. تفاصيل التسوية تعرض `performedById`, `performedByNameSnapshot`, `recordedAt`, `reason`, الحركة المرجعية والحركة الناتجة. القراءة للتاجر تضيف شرط `merchantId` على استعلام قاعدة البيانات؛ المعرف الأجنبي يرجع 404 أو قائمة خالية، وطلب فلتر تاجر آخر يرجع 403.

الشحنات والمرتجعات أصبحت منفذة وفق [عقد الشحنات](shipments-api.md) و[عقد المرتجعات](returns-api.md). الاستلام الفعلي للمرتجع يسجل العهدة دون زيادة المتاح؛ فحص GOOD أو قبول NOTED يثبت RETURN_IN. هذا مختلف عن الاستلام الأول الموصوف في هذا العقد.

## التحقق الذي نُفذ

اختبارات التكامل تشمل تسجيل الاستلام والملاحظات ووقت المنفذ، إعادة المفتاح متسلسلًا ومتزامنًا، منع تغيير الطلب أو صاحبه مع المفتاح نفسه، استلامين متزامنين لأول رصيد، عزل التاجر، صلاحيات التسوية وحدود الرصيد، ورفض تعديل أو حذف التاريخ مباشرة. فحوص التنفيذ الأخيرة: 85 اختبار HTTP، و4 اختبارات وحدة، و53 اختبار قيد قاعدة بيانات، مع نجاح build وlint وPrisma validate. طبّق ترحيل المخزون على `stocked_dev` المحلية وأظهر Prisma أن المخطط محدث.

## امتداد المواقع والجرد — 9 أكتوبر 2026

التسويات اليدوية، زيادة أو نقصان، أصبحت للمدير فقط في Controller والخدمة وSQL. الاستلام والتسوية يحتاجان placements كاملة على أرفف تاجر الصنف. تسوية فرق الجرد لها stocktakeLineId بدل referenceMovementId ولا تنفذ من endpoint التسوية اليدوية؛ يثبتها اعتماد المدير ذريًا. راجع [عقد المواقع](storage-locations-api.md) و[عقد الجرد](stocktakes-api.md). أي جرد نشط يمنع كتابات هذا العقد حتى الإغلاق أو الإلغاء.


## OpenAPI للاستلام والتسويات — تحديث 2026-10-09

- POST receipts وstock-adjustments يعلنان Idempotency-Key مطلوبًا (UUIDv4 في التحقق)، وresponse schema نفسها للإنشاء201 ولإعادة الطلب المطابق200. الرد ليس wrapper؛ هو المستند نفسه كما كان.
- GET list/detail للاستلام والتسويات يعلنان نماذج محددة؛ list هو `{items,total,page,limit}` وitems بنفس تمثيل detail. GET لا يحتاج Idempotency-Key.
- ReceiptResponseDto يوثق header والمنفذ/اسمه/وقت الاستلام والملاحظات، وكل بند بموضعه والصنف/اسمه/رمزه وحالته وعيبه وملاحظاته ومرجع الحركة.
- AdjustmentResponseDto يوثق الصنف والتاجر والمنفذ والتوقيت والسبب والاتجاه والكمية وquantityDelta والحركة الناتجة، مع referenceMovementId أو stocktakeLineId حسب المصدر (المصدر الآخر null). اعتماد الجرد فقط ينشئ المصدر الثاني، لا POST التسوية اليدوية.
- نماذج الاستجابة تصف select الفعلي دون password/session/idempotency hash fields. نطاق التاجر داخل queries مستمر؛ لا تغيير permissions أو ledger أو JSON.
- اختبارات عقد القراءة تقارن Swagger بالـ JSON الحقيقي، بما فيه القيم nullable ومصادر الحركة المتداخلة وكل مراحلها. نتائج الفحوص الحالية موثقة في BACKEND_PROGRESS؛ الأرقام تحت «التحقق الذي نفذ» أعلاه تخص مرحلة المخزون التاريخية ولا تعني إعادة تشغيلها الآن.
