# الشحنات: تسجيل الطلب → التجهيز → الخروج

كل المسارات تحت `/api/v1` وتتطلب جلسة Bearer صالحة وحسابًا نشطًا وكلمة مرور تم تغييرها. المدير وأمين المخزن والموظف يسجلون العمليات؛ التاجر يقرأ شحناته فقط. لا Firebase، ولا تعديل لـFlutter في هذه المرحلة.

## القواعد التشغيلية

- كل شحنة تتبع تاجرًا واحدًا، وكل بند يجب أن يكون صنفًا نشطًا يملكه ذلك التاجر. لا تكرار للصنف في الطلب؛ تجمع كميته في بند واحد.
- رقم الشحنة `SH-000001` مستقل عن أكواد الأصناف مثل `MZ-000001`. الشحنة ليست صنفًا جديدًا ولا تستهلك عداد التاجر.
- التسجيل والتجهيز لا يحجزان ولا يخصمان المخزون. الكمية تفحص عند الخروج فقط؛ يمكن أن يبقى طلب مجهزًا بسبب نقص الرصيد.
- الخروج كامل لكل البنود مرة واحدة. فشل أي بند يلغي مستند الخروج وجميع الحركات والخصم معًا.
- كل مرحلة مستند ثابت باسم المنفذ ونسخة اسمه ووقت قاعدة البيانات. لا تعدّل الأحداث بعد تغيير أسماء الأشخاص أو الأصناف.
- أسماء شركة الشحن ورقم التتبع تسجل يدويًا عند الخروج؛ `DISPATCHED` تعني خرجت من المخزن، ولا تعني وصولها للعميل.
- الإلغاء، الخروج الجزئي، المرتجعات، ربط شركات الشحن، الإشعارات وواجهة Flutter خارج هذه الدفعة. الطلب الخاطئ يبقى مسجلًا ولا يُخرج. تعطيل التاجر يمنع تنفيذ مراحل جديدة حتى إعادة تفعيله، ويبقي التاريخ متاحًا للفريق.
- لا تصحح حركة خروج بتسوية استلام: التسويات الحالية مرجعها استلام أصلي فقط. معالجة خروج خاطئ تحتاج دورة تصحيح/مرتجع مستقلة.

## تسجيل الطلب

`POST /shipments` مع `Idempotency-Key` من نوع UUID v4 جديد:

```json
{
  "merchantId": "<merchant UUID>",
  "notes": "طلب رقم 123",
  "lines": [{ "itemId": "<item UUID>", "quantity": 4 }]
}
```

من 1 إلى 100 بند، وكمية صحيحة من 1 إلى 1,000,000. الملاحظات اختيارية حتى 2000 حرف. جسم HTTP بحد16KiB بالبايت الفعلي؛ النص العربي وescapes والمسافات قد تؤثر في الحجم. تتجاوز الحد؟ الاستجابة413 ويجب تقليل الجسم. يرسل العميل المعرف والكمية فقط؛ لا أسماء أصناف أو هوية موظف أو أوقات أو حالة أو رقم شحنة.

الاستجابة201 تحتوي `id/code/merchantId/merchantNameSnapshot/registeredById/registeredByNameSnapshot/registeredAt/notes/lines`. كل بند يحتوي `id/itemId/position/itemCodeSnapshot/itemNameSnapshot/quantity`. استجابة التسجيل مستند ثابت؛ لمعرفة الحالة الحالية استخدم GET.

## التجهيز

`POST /shipments/:id/prepare` مع مفتاح مستقل وجسم `{}` أو بلا جسم. لا تقبل أي حقول إضافية.

الاستجابة201: `id/shipmentId/preparedById/preparedByNameSnapshot/preparedAt`. التجهيز يتطلب تاجرًا نشطًا ولا يمكن تسجيله مرتين.

## الخروج من المخزن

`POST /shipments/:id/dispatch` مع مفتاح مستقل:

```json
{ "carrierName": "Bosta", "trackingNumber": "001-AB" }
```

الشركة نص غير فارغ حتى200 حرف، والتتبع نص غير فارغ حتى150 حرف؛ تبقى الأصفار والحروف. لا نفرض تفردًا عالميًا لرقم التتبع.

الاستجابة201: `id/shipmentId/preparationId/dispatchedById/dispatchedByNameSnapshot/dispatchedAt/carrierName/trackingNumber`. يشترط التجهيز السابق، وعدم وجود خروج، ونشاط التاجر والأصناف، ورصيد كافٍ لكل البنود بعد الأقفال. تحفظ حركة `SHIPMENT_OUT` سالبة لكل بند وتحدث الأرصدة داخل المعاملة نفسها.

## إعادة الطلب والتعارض

يستخدم كل إجراء مفتاحًا مستقلًا. إعادة نفس المفتاح بنفس الكاتب والمدخلات بعد تطبيع UUID والنصوص تعيد مستند الإجراء الأصلي بـ200، حتى لو انتقلت الشحنة لمرحلة لاحقة. تغيير الكاتب أو المحتوى مع المفتاح نفسه يرجع409. استخدام مفتاح جديد لمرحلة مكتملة يرجع409. بعد فقد الاستجابة، أعد نفس المفتاح؛ لا تنشئ مفتاحًا جديدًا لتجاوز التعارض. صلاحية الجلسة والدور تفحص مجددًا حتى عند الإعادة.

## قراءة الشحنات وتتبع الأصناف

`GET /shipments` يعيد `{items,total,page,limit}`؛ الصفحة1 والحد25 افتراضيًا والحد الأقصى100. الفلاتر:

| الحقل | المعنى |
| --- | --- |
| merchantId | تاجر محدد للفريق؛ التاجر لا يستطيع طلب غير تاجره |
| itemId | الشحنات التي تحتوي هذا الصنف، ضمن نطاق التاجر |
| status | REGISTERED / PREPARED / DISPATCHED؛ مشتقة من المستندات |
| actorId | المنفذ في أي مرحلة من الثلاث |
| from / to | تاريخ تسجيل الطلب: from شامل وto غير شامل؛ from قبل to |
| page / limit | الترقيم؛ الأحدث أولًا ثم UUID تنازليًا |

`GET /shipments/:id` يعيد مستند التسجيل وبنوده، و`preparation` و`dispatch` (null قبل تسجيلهما)، و`status` و`timeline`. كل خطوة في الخط الزمني تحتوي `step/actorId/actorNameSnapshot/recordedAt`؛ يظهر اسم الشركة ورقم التتبع في `dispatch`.

مثال: للتاجر صنف `MZ-000001`، يقرأ قائمة الشحنات بفلتر `itemId` ثم يفتح الشحنة ليعرف من سجل الطلب ومن جهزه ومن أخرجه ووقت كل مرحلة. الاستلام الأصلي يبقى في سجل الاستلام وحركات الصنف؛ الشحنة لا تحدد قطعة فردية أو دفعة استلام بعينها لأن المخزون مجمع حسب الصنف.

`GET /movements?kind=SHIPMENT_OUT&itemId=...` يعرض مصدر حركة الخروج في `shipmentLine` و`shipmentDispatch` مع معرف الشحنة والتتبع. الحركة خارج ملكية التاجر ترجع404؛ لا يكشف مجرد معرفة UUID بيانات الآخرين. فلتر تاجر آخر يرجع403.

## ضمانات قاعدة البيانات والصيانة

الجداول الخمسة: `shipments/shipment_lines/shipment_code_sequences/shipment_preparations/shipment_dispatches`. المفاتيح المركبة تربط البنود بالتاجر والصنف والشحنة، والخروج بإثبات تجهيز الشحنة نفسها. تمنع SQL تعديل/حذف المستندات، وإضافة بنود بعد تثبيت التسجيل، والخروج دون جميع الحركات أو مع خصم/فاعل/وقت/مصدر غير مطابق.

ترحيل أول يضيف enum فقط، ثم ترحيل ثان ينشئ الجداول والقيود. لا تعديل لترحيل سابق ولا حذف بيانات. الإسقاط يحدث عبر StockPostingService؛ قيود SUM الحالية تتحقق من كل الأنواع ولا تخصم مرة ثانية.

الخدمات منفصلة: التسجيل، التجهيز، الخروج، القراءة، تخصيص الرقم. تفويض الكاتب وإعادة فحص الجلسة وأقفال الرصيد يعاد استخدامها من طبقة المخزون. إضافة مرحلة مستقبلية تتطلب مستندها وقيودها وAPI واختباراتها؛ لا تحتاج تعديل الحدث التاريخي.

العقد موثق أيضًا في Swagger المحلي `/api/docs`. التحقق: `npm run build`، `npm run lint`، `npm test`، `npm run test:e2e`، `npm run test:db` و`npx prisma validate`. الاختبارات تنشئ قواعد محلية عشوائية وتحذفها؛ لا reset على stocked_dev.
