# إدارة المستخدمين والتجار — عقد API وتعليمات الاستخدام

**الحالة: منفذ محليًا وفق البلوبرنت المعتمد.**
كل المسارات تحت /api/v1، وتتطلب حساب ADMIN فعّالًا وجلسة صالحة أكملت تغيير كلمة المرور الإلزامي.
المرحلة تستخدم جداول الهوية الموجودة؛ لا حزمة أو جدول أو ترحيل جديد.

## بدء التجربة بالترتيب

1. شغّل PostgreSQL والتطبيق وفق README. لأول مرة فقط، أنشئ مديرًا بواسطة npm run admin:bootstrap.
2. افتح http://127.0.0.1:3000/api/docs في بيئة التطوير.
3. نفّذ POST /api/v1/auth/login بالبريد وكلمة المرور الخاصة بك.
4. انسخ token إلى Authorize؛ أدخل الرمز نفسه، وSwagger يضيف Bearer تلقائيًا.
5. إذا كانت mustChangePassword=true، نفّذ auth/change-password، ثم استبدل الرمز في Authorize بالرمز الجديد.
6. أنشئ التاجر أولًا إذا كنت ستنشئ حسابًا بدور MERCHANT، ثم استخدم معرف التاجر في إنشاء حسابه.
7. أنشئ حسابات الموظفين وأمين المخزن، وجرّب عرضها وفلاترها وتعديلها.

لا توجد حسابات جاهزة بكلمات مرور منشورة. لا تسجل بيانات الدخول أو تنسخها إلى ملفات التوثيق.
Swagger معطل في الإنتاج، والنشر له إعدادات وأمان منفصلان موضحان في دليل المصادقة.

## الصلاحيات

| الدور | مسارات إدارة المستخدمين والتجار |
|---|---|
| ADMIN | الإنشاء والقراءة والتعديل والتعطيل ضمن قواعد الحماية |
| WAREHOUSE_KEEPER | ممنوعة في هذه المرحلة |
| EMPLOYEE | ممنوعة في هذه المرحلة |
| MERCHANT | ممنوعة؛ بوابة قراءة بياناته ومخزونه تنفذ مع ميزات الأعمال |

حساب ADMIN الملزم بتغيير كلمة المرور لا يدخل الإدارة حتى يكمل التغيير. لا حقول permissions أو دور حر يرسله العميل.

## إنشاء حساب

POST /users → 201

```json
{
  "email": "staff@example.com",
  "displayName": "اسم الموظف",
  "initialPassword": "<a private initial password chosen by the administrator>",
  "role": "EMPLOYEE"
}
```

لإنشاء حساب تاجر: role=MERCHANT مع merchantId لتاجر موجود وفعّال. للأدوار الأخرى يحذف merchantId أو يرسل null.
الأدوار المتاحة: ADMIN، WAREHOUSE_KEEPER، EMPLOYEE، MERCHANT.

- البريد يطبّع إلى lowercase بعد trim ويجب أن يكون فريدًا.
- كلمة المرور الأولية تخضع لسياسة 15–128 محرفًا وArgon2id والقائمة المحلية الحالية، ولا تعاد في الاستجابة أو logs.
- mustChangePassword=true دائمًا عند الإنشاء. يسلّم المدير بيانات البداية للمستخدم خارج النظام؛ لم تنفذ رسائل بريد أو SMS.
- createdById من المدير الموثوق ووقت الإنشاء من القاعدة؛ لا يقبل العميل تحديدهما.
- مسار POST /users خاص بالمدير، وليس تسجيلًا ذاتيًا.

الاستجابة تحتوي فقط: id، email، displayName، role، merchantId، isActive، mustChangePassword، createdById، createdAt، updatedAt.
createdById قد يكون null لحساب المدير الأول فقط وفق إجراء التهيئة الموجود؛ لا يمكن تحديده يدويًا عبر API.

## عرض الحسابات والفلاتر

GET /users/:id → تفاصيل حساب واحد.

GET /users?page=1&limit=25&isActive=true&role=EMPLOYEE

الفلاتر الاختيارية: role وisActive وmerchantId وsearch؛ البحث في الاسم والبريد دون حساسية لحالة الأحرف.
الاستجابة:

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "limit": 25
}
```

page عدد صحيح من 1 إلى 1000000، وlimit من 1 إلى 100 وافتراضيًا 25. isActive يقبل true أو false فقط؛ النص false لا يتحول إلى true.
الترتيب createdAt ثم id تنازليًا. عناصر الصفحة وعددها الإجمالي يقرآن من snapshot واحدة لكل طلب؛ تغير البيانات بين طلبات صفحات مختلفة يمكن أن يحرك حدود الصفحات كالمعتاد في offset pagination.
لا روابط جلسات أو hashes ضمن القائمة أو التفاصيل.

## تعديل الحساب

PATCH /users/:id → 200

الحقول المسموحة: email وdisplayName وrole وmerchantId. يجب إرسال حقل واحد على الأقل.
لا يسمح بتعديل isActive أو passwordHash أو initialPassword أو createdById هنا.

```json
{ "displayName": "اسم بعد التعديل" }
```

```json
{ "role": "EMPLOYEE", "merchantId": null }
```

المثال الثاني ضروري عند نقل حساب من MERCHANT لدور آخر: إزالة ارتباط التاجر يجب أن تكون صريحة.
نقل موظف إلى MERCHANT يحتاج merchantId صالحًا وفعّالًا. تغيير التاجر المرتبط يعيد فحصه.
يمكن تصحيح اسم حساب مرتبط بتاجر معطل دون إنشاء ارتباط جديد أو تفعيل الحساب/التاجر.

تغيير البريد أو الدور أو التاجر المرتبط يبطل جميع جلسات الحساب ذريًا. تغيير الاسم فقط يحافظ عليها. إعادة إرسال القيم الحساسة نفسها لا تبطل الجلسات ما دامت لم تتغير فعليًا.
إذا عدّل المدير بريده أو دوره، تنجح العملية ثم يحتاج تسجيل الدخول مرة أخرى؛ الجلسة الحالية لا تبقى مميزة.
الدخول الذي بدأ بالبريد القديم وتزامن مع تغييره يعاد فحص البريد قبل إصدار الجلسة ويرفض.

## حالة الحساب وحماية آخر مدير

PATCH /users/:id/status → 200

```json
{ "isActive": false }
```

تعطيل الحساب يبطل كل جلساته في المعاملة نفسها. إعادة التفعيل تستخدم true، ولا تعيد صلاحية أي رمز قديم.
لا يمكن تعطيل آخر ADMIN فعّال أو تحويله إلى دور آخر. حسابات ADMIN المعطلة لا تدخل عدد المديرين الفعّالين.
يمكن للمدير تعطيل نفسه أو تغيير دوره إذا بقي مدير فعّال آخر؛ ينتهي تفويض جلسته بعد العملية.
طلبان متزامنان لا يمكن أن يزيلا آخر مدير: العملية التي تكسر القاعدة تحصل على 409.

## إنشاء التاجر

POST /merchants → 201

```json
{ "code": "MZ", "name": "اسم التاجر", "phone": "+201001234567" }
```

- code يحدد مرة واحدة؛ يطبّع إلى uppercase بعد trim، ويكون 2–8 حروف A–Z وفريدًا.
- name بطول 1–200 بعد trim، وphone نص بطول 1–32 بعد trim؛ يحتفظ بالأصفار وعلامة +.
- التاجر كيان مالك للبضاعة؛ الإنشاء لا يضيف حساب دخول تلقائيًا. يمكن ربط أكثر من حساب به.
- createdById من المدير؛ حالة البداية فعّالة.
- الاستجابة: id، code، name، phone، isActive، createdById، createdAt، updatedAt.

## قراءة التاجر وتعديله وحالته

GET /merchants/:id → بيانات التاجر.

GET /merchants?page=1&limit=25&isActive=false&search=MZ → نفس شكل الصفحات؛ البحث في code وname وphone.

PATCH /merchants/:id → يقبل name وphone فقط. إرسال code أو PATCH فارغ يرفض بـ400، وTrigger القاعدة يظل يمنع تغيير الرمز مباشرة في SQL أيضًا.

PATCH /merchants/:id/status → يقبل isActive boolean.
تعطيل التاجر يبطل جلسات كل حساباته، دون المساس بحسابات تاجر آخر. حالة isActive الفردية لكل حساب تظل محفوظة.
إعادة تفعيل التاجر لا تعيد الجلسات القديمة ولا تفعّل مستخدمًا معطلًا فرديًا.
لا يوجد DELETE للمستخدمين أو التجار؛ السجلات والعلاقات تبقى محفوظة.

## الأخطاء

| الحالة | الاستخدام |
|---|---|
| 400 | حقول غير صحيحة أو زائدة أو null غير مسموح أو UUID غير صالح أو PATCH فارغ أو علاقة دور/تاجر غير صحيحة |
| 401 | جلسة منتهية/مبطلة أو حساب معطل |
| 403 | ليس مديرًا أو لم يكمل تغيير كلمة المرور؛ يشمل إعادة الفحص داخل الكتابة |
| 404 | المستخدم أو التاجر غير موجود بعد التحقق من صلاحية المسار |
| 409 | بريد/رمز مكرر، أو آخر مدير فعّال، أو محاولة ارتباط جديد بتاجر معطل |
| 500 | خطأ داخلي عام؛ لا SQL أو تفاصيل Prisma في الاستجابة |

تكرار البريد أو الرمز يعالج أيضًا عند تسابق طلبين، اعتمادًا على قيد unique في القاعدة. حراس الدخول والتحقق من حجم الطلب الحالية تظل مطبقة.

## مكان اللوجيك وضمان المعاملة

```text
HTTP → Guards → DTO → Controller → UsersService / MerchantsService
                                → AdminMutationService
                                → locked reauthorization → Prisma/PostgreSQL
```

- users/ يملك قواعد الحساب وعلاقة دوره بالتاجر وقاعدة آخر مدير، وmerchants/ يملك قواعد بيانات التاجر وحالته.
- admin-mutation.service.ts ينسق بروتوكول المعاملة فقط: advisory lock مشترك للكتابات الإدارية ثم صفوف الفاعل والمستخدمين المتأثرين بترتيب ثابت، ثم فحص جلسة المدير ودوره الحالي من القاعدة.
- تعداد حسابات التاجر يحدث بعد القفل الإداري؛ إنشاء الحسابات ونقلها يستخدم القفل نفسه. لا توجد نافذة تظهر فيها حسابات مرتبطة خارج عملية الإبطال.
- SessionService ينفذ إبطال الجلسات داخل المعاملة التي يملكها المستدعي، ووقت الإبطال من PostgreSQL.
- التجزئة المكلفة تتم قبل فتح المعاملة، بينما قرار السماح الحاسم يتكرر داخلها بعد انتظار الأقفال.
- عند فشل الإبطال أو الكتابة، يتراجع التعديل بالكامل. لا يوجد تعطيل محفوظ مع جلسات بقيت بسبب فشل جزئي.
- البروتوكول يفترض أن كل كود كتابة إدارية يستخدم AdminMutationService. تعديل يدوي مباشر في DB يتجاوز قواعد التطبيق؛ حساب تشغيل DB محدود جزء من إعداد الإنتاج.
- القفل المشترك مناسب لحجم الإدارة الحالي. لا تستخدمه لحركات المخزون المستقبلية؛ لها قفل معاملات وتصميمها الخاص.

## سجل الأمان

الأحداث: user.created، user.updated، user.role_changed، user.enabled، user.disabled، merchant.created، merchant.updated، merchant.enabled، merchant.disabled.
تسجل بعد نجاح المعاملة مع actorId وtargetId فقط، دون كلمة مرور أو بريد أو token أو body الطلب.
هذه logs أمنية وليست دفتر تدقيق دائمًا لكل تغيير قيمة. دفتر حركات المخزون غير القابل للتعديل والإعداد التشغيلي لحفظ logs مرحلتان لاحقتان.

## التحقق والمراجعة

- اختبارات مستخدمين: صلاحيات الأدوار لكل المسارات، إنشاء الأدوار الأربعة، منع تسرب كلمة البداية، تضارب البريد، علاقة التاجر، إبطال الجلسات، آخر مدير، rollback، فحص فاعل تغير أثناء انتظار القفل، وسباق الدخول مع التعطيل/تغيير البريد.
- اختبارات تجار: تثبيت الرمز، المدخلات، تضارب الرمز، إبطال حسابات تاجر دون غيره، حفظ التعطيل الفردي، rollback، منع ارتباط أثناء تعطيل متزامن، وسباق الدخول مع تعطيل التاجر.
- قواعد اختبار عشوائية منفصلة. لا حسابات تشغيل أو بيانات تجار تضاف إلى stocked_dev من الاختبارات.
- مراجعة مصدر مستقلة بواسطة وكيل Codex داخل المهمة دون .env أو مشاركة خارجية: لا ملاحظات قابلة للتنفيذ؛ المراجع لم يدع تشغيل الاختبارات.

الأوامر: npm run build، npm run lint، npm test، npm run test:e2e، npm run test:db، npx prisma validate، npx prisma migrate status.
نتائج التحقق في تنفيذ هذه المرحلة:

- npm run build وnpm run lint: نجحا دون أخطاء أو تحذيرات lint.
- npm run test:e2e: 50 حالة ناجحة: 20 للمصادقة، و21 للمستخدمين، و9 للتجار.
- npm test: 4 حالات ناجحة لكلمة المرور.
- npm run test:db: 28 نتيجة ناجحة حسب node:test، تشمل 27 حالة فرعية والمجموعة الرئيسية.
- prisma validate وmigrate status: الشيما صالحة والقاعدة مواكبة للترحيلين الموجودين؛ لا ترحيل جديد لهذه المرحلة.
- git diff --check: نجح.
- قواعد الاختبار المتبقية بعد التشغيل: صفر.
- فحص قاعدة التطوير بعد الاختبارات: حساب واحد، وصفر تجار وصفر جلسات؛ لا حاجة لحذف الحساب أو إعادة تهيئة القاعدة.
- فحص 176 ملفًا متتبعًا أو قابلًا للتتبع ضد قيم أسرار البيئة المحلية: لا تطابقات، دون طباعة أي سر.
- تحذير Vite الخاص بـvite-tsconfig-paths استمر دون فشل؛ لم تغير أدوات البناء في هذه المرحلة.
