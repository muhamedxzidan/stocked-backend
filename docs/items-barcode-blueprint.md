# مخطط تنفيذ الأصناف والباركود

الحالة: اعتمده المستخدم ثم نُفّذ في 9 أكتوبر 2026. العقد والنتائج الحالية في [items-api.md](items-api.md). بقية الملف تحتفظ بالمخطط الذي تم اعتماده.

## الهدف والنطاق

إنشاء دليل أصناف مستقل لكل تاجر، وكود محلي ثابت يبدأ برمز التاجر مثل `MZ-000001`. إنشاء الصنف لا يضيف أي كمية. الرصيد سيأتي لاحقاً من الاستلام وحركات المخزون، وليس من حقل قابل للتعديل داخل الصنف.

يشمل التنفيذ إنشاء الأصناف، قراءتها والبحث عنها بالكود، تعديل بياناتها المسموح بها وتعطيلها، وإرجاع بيانات ملصق الباركود. لا يشمل تعديل Flutter أو تكامل شركات الشحن أو حجز المخزون. توليد الملصق بصرياً وطباعته واختبار القارئ الفعلي مرحلة تالية؛ بيانات الملصق ستكون جاهزة لها.

## الوضع الحالي ومسار الطلب

التطبيق الحالي NestJS مع PostgreSQL وPrisma. توجد حسابات وجلسات، وصلاحيات تُراجع على الخادم، وإدارة للمستخدمين والتجار، وإلغاء جلسات الحسابات عند تغييرات الأمان. لا توجد جداول أصناف أو أرصدة بعد.

المسار: HTTP → حراس الجلسة وتغيير كلمة المرور والدور → Controller للتحقق من الطلب → Service لقواعد العمل → Prisma transaction → PostgreSQL → استجابة محددة الحقول.

صلاحيات الكتابة تُراجع مجدداً داخل المعاملة بعد أخذ الأقفال، حتى لا يُنفذ طلب قديم بعد تعطيل المستخدم أو تغيير دوره.

## الجداول المقترحة

### Item

| الحقل | النوع والقيد | الغرض |
| --- | --- | --- |
| id | UUID من قاعدة البيانات | هوية ثابتة |
| merchantId | UUID، FK Restrict، ثابت | مالك الصنف |
| ordinal | BigInt موجب، فريد مع merchantId، ثابت | الرقم المتسلسل |
| code | نص حتى 40 حرفاً، فريد وثابت | الباركود المحلي |
| name | نص مطلوب حتى 200 حرف | اسم الصنف |
| brand | نص حتى 100 حرف أو null | الماركة |
| color | نص حتى 100 حرف أو null | اللون |
| weightKg | Decimal(12,3) موجب | الوزن بالكيلوجرام |
| notes | نص اختياري حتى 2000 حرف | ملاحظات تعريفية |
| active | Boolean، افتراضياً true | التعطيل بدلاً من الحذف |
| createdById | UUID، FK Restrict، ثابت | المستخدم الذي أنشأ الصنف |
| createdAt | وقت قاعدة البيانات، ثابت | وقت الإنشاء |
| updatedAt | وقت التعديل من الخادم | آخر تعديل |

قرارات تحتاج اعتماد هذا المخطط: الوزن بالكيلوجرام، وإرساله كنص عشري دون تقريب صامت؛ الماركة واللون يمكن أن يكونا null عندما لا ينطبقان على الصنف. لا يُقبل وزن صفر أو سالب أو أكثر من ثلاث خانات عشرية.

لا يُقبل merchantId أو code أو ordinal أو بيانات المنشئ كتعديلات لاحقة. توجد قيود قاعدة بيانات للأرقام والأسماء والعلاقات، وقيود تمنع تغيير الهوية والكود والمالك والمنشئ. يُتحقق من تطابق الكود مع رمز التاجر ورقم الصنف داخل قاعدة البيانات عند الإنشاء.

### ItemCodeSequence

merchantId مفتاح أساسي وعلاقة بالتاجر، وlastValue رقم BigInt غير سالب. جدول مستقل لأن تخصيص أرقام الأصناف مسؤولية منفصلة عن بيانات التاجر.

تخصيص الرقم وإنشاء الصنف في معاملة واحدة باستخدام تحديث ذري للعداد. الطلبات المتزامنة لا تحصل على الرقم نفسه. الرقم يُعرض بست خانات على الأقل؛ بعد 999999 يصبح 1000000 دون قطع أو تدوير. الأرقام التي تم حفظ أصنافها لا يعاد استخدامها عند التعطيل. فشل المعاملة يلغي تخصيصها أيضاً. الوصول للحد الأقصى يرفض الإنشاء بوضوح.

## الصلاحيات المقترحة

| العملية | مدير النظام | أمين المخزن | موظف المخزن | التاجر |
| --- | --- | --- | --- | --- |
| إنشاء صنف لتاجر نشط | نعم | نعم | نعم | لا |
| قراءة الأصناف والبحث والملصق | كل التجار | كل التجار | كل التجار | أصنافه فقط |
| تعديل البيانات الوصفية أو التعطيل | نعم | لا | لا | لا |
| تغيير المالك أو الكود أو حذف الصنف | لا | لا | لا | لا |

تقييد تعديل البيانات وتعطيل الأصناف بالمدير مقترح محافظ يحتاج اعتمادك؛ الوثيقة أعطت الموظف إضافة الأصناف دون أن تحدد تعديلها. يمكن توسيع الصلاحية بعد الاتفاق.

عزل التاجر يكون في استعلام قاعدة البيانات نفسه باستخدام merchantId من الجلسة، وليس من بيانات يرسلها العميل. الوصول لصنف تاجر آخر بالهوية أو الكود أو الملصق يرجع 404. فلتر تاجر مختلف في بوابة التاجر يُرفض دون كشف وجوده. تعطيل الصنف يحفظ تاريخه؛ لا يمس رصيده أو حركاته المستقبلية.

## واجهات API

- POST /api/v1/items: إنشاء بيانات الصنف وربطه بتاجر نشط.
- GET /api/v1/items: صفحات محدودة وفلاتر التاجر والحالة والبحث بالاسم والكود والماركة واللون.
- GET /api/v1/items/by-code/:code: البحث الدقيق بقارئ الباركود؛ يسجل قبل مسار الهوية.
- GET /api/v1/items/:id: التفاصيل وفق نطاق المستخدم.
- GET /api/v1/items/:id/label: الكود واسم الصنف والتاجر ونوع CODE128، وفق نفس عزل القراءة.
- PATCH /api/v1/items/:id: البيانات الوصفية فقط للمدير.
- PATCH /api/v1/items/:id/status: التعطيل أو التفعيل للمدير.

جميع الطلبات ترفض الحقول غير المعروفة. الاستجابة تحول Decimal إلى نص ولا تسرّب BigInt أو حقول داخلية. إعادة طلب الملصق لا تنشئ صنفاً أو كوداً جديداً. فلاتر التصفح لها ترتيب ثابت وحد أقصى لحجم الصفحة.

## المسؤوليات والملفات

- prisma/schema.prisma: إضافة Item وItemCodeSequence والعلاقات فقط.
- prisma/migrations/<new>/migration.sql: ترحيل جديد وقيود SQL؛ لا تعديل للترحيلات السابقة.
- src/items/items.module.ts: ربط المكونات.
- src/items/items.controller.ts: المسارات والصلاحيات والتحقق من الطلبات.
- src/items/items.service.ts: قواعد الإنشاء والقراءة والتعديل وحدود الملكية والمعاملات.
- src/items/item-code.service.ts: تخصيص الرقم وتنسيق الكود فقط.
- src/items/item-selection.ts: الحقول الآمنة المختارة.
- src/items/item-response.mapper.ts: تحويل أرقام قاعدة البيانات للاستجابة.
- src/items/dto/: ملف مستقل لكل طلب واستجابة ذات مسؤولية واضحة.
- src/app.module.ts: إضافة الوحدة.
- test/items/: اختبارات API والأدوار والعزل والتزامن.
- test/database/: اختبارات القيود في قاعدة معزولة.
- docs/items-api.md: توثيق العقد والأمثلة بعد التنفيذ.

لا تُضاف طبقات عامة أو حزم جديدة دون حاجة فعلية.

## المعاملات والتزامن

الإنشاء: قفل صف المستخدم → التحقق من الجلسة والدور وحالة الحساب → قفل قراءة مشترك لصف التاجر والتحقق من نشاطه → تخصيص الرقم ذرياً → إنشاء الصنف → commit.

هذا يسمح بإنشاء أصناف متزامنة لتجار مختلفين، ويتسلسل تخصيص الأرقام للتاجر نفسه. قفل التاجر يمنع تعطيله أثناء إنشاء الصنف. لا يستخدم إنشاء الموظفين قفل إدارة المستخدمين العام.

تعديلات المدير تستفيد من AdminMutationService الحالي لإعادة التحقق من صلاحية المدير داخل المعاملة، ثم قفل التاجر والصنف بترتيب ثابت. يُراجع ترتيب الأقفال مقابل تعطيل التاجر وتغيير الأدوار قبل التنفيذ، ولا يُعتمد على حراس HTTP وحدها.

## الملاحظات والتالف

ملاحظات الصنف تعريفية؛ حالة كل دفعة واردة أو مرتجع تُسجل لاحقاً في عملية الاستلام أو الفحص نفسها: نوع الضرر، الكمية المتأثرة، ووصف واضح للكسر أو الخدش. لا تُختزل حالة دفعات متعددة في ملاحظة واحدة على الصنف.

البضاعة ذات الملاحظات تُستلم وتُوثق. المرتجع ذو الملاحظات يبقى بانتظار اعتماد الأمين أو المدير قبل إضافته للمتاح. تحديد التصرف في بضاعة غير صالحة للبيع يُعتمد ضمن مخطط الاستلام والمرتجعات، دون إضافة رصيد تالف مستقل في المرحلة الأولى أو اعتبار كل بضاعة معيبة قابلة للصرف تلقائياً.

## خطوات التنفيذ بعد الاعتماد

1. مراجعة العقود والصلاحيات وترتيب الأقفال مع الخدمات الحالية.
2. إضافة الجدولين وترحيل جديد واختبار القيود دون مسح بيانات التطوير.
3. تنفيذ تخصيص الأكواد والمعاملات والقراءة المقيدة بالتاجر.
4. إضافة المسارات وDTO وتوثيق Swagger.
5. اختبار العزل والتزامن والتراجع عند الفشل وتوثيق الاستخدام.
6. مراجعة مستقلة عند الحاجة، ثم التقرير والرفع إلى GitHub.

## القبول والاختبارات

- تاجر لا يقرأ صنف غيره عبر القائمة أو الهوية أو الكود أو الملصق.
- الموظف والأمين يضيفان أصنافاً دون إدارة بيانات التجار أو المستخدمين.
- إنشاء متزامن لنفس التاجر يعطي أكواداً فريدة؛ تجار مختلفون لهم عدادات مستقلة.
- اختبار الانتقال من 999999 إلى 1000000، وفشل المعاملة دون حفظ جزئي.
- تعطيل الحساب أو إلغاء جلسته أو تغيير دوره أثناء انتظار الطلب يمنع الكتابة.
- تعطيل التاجر يتزامن بصورة صحيحة مع الإنشاء، ولا يقبل الإنشاء بعد تعطيله.
- منع تغيير الكود والمالك والمنشئ، والتحقق من الوزن والحقول الإضافية.
- إنشاء صنف لا ينشئ حركة أو كمية مخزون.
- نجاح build وlint واختبارات الوحدات وAPI وقاعدة البيانات مع الاحتفاظ بالاختبارات السابقة.

تم التنفيذ بعد موافقة المستخدم الصريحة، وفق بوابة الموافقة الحالية.
