# بلوبرنت إدارة المستخدمين والتجار

**الحالة: اعتمد المستخدم الخطة ونفذت مرحلة الإدارة محليًا. العقد ونتائج التحقق في admin-api.md.**
**النطاق: stocked-backend فقط؛ مرحلة تالية للمصادقة المنفذة.**

## الهدف
تمكين مدير النظام من إنشاء حسابات الفريق والتجار، وضبط الأدوار والتعطيل، مع منع فقدان آخر مدير فعّال وإبطال الجلسات عند تغيير صلاحيات الحساب.
لا حذف نهائي للمستخدم أو التاجر؛ تبقى العلاقات والسجلات محفوظة.

## الوضع الحالي ونقطة التغيير
الجداول الموجودة: User وMerchant وSession وLoginAttemptBucket.
الخدمات الموجودة: PasswordService للتجزئة والسياسة، SessionService لفحص الجلسة والإبطال، SecurityAuditService لسجل الأمان.
SessionGuard ثم PasswordChangeGuard ثم RolesGuard تحمي الطلبات عالميًا.
لا توجد endpoints لإدارة المستخدمين أو التجار. AuthModule يصدّر PasswordService وSecurityAuditService؛ سنصدّر SessionService لإعادة استخدام الفحص الموثوق داخل المعاملة.
نضيف وحدتي Users وMerchants ونربطهما في AppModule. لا تغيير في الشيما أو الترحيلات لهذه المرحلة ما دام التنفيذ يطابق التصميم الحالي.

## تدفق الطلب
```text
HTTP
  -> SessionGuard / PasswordChangeGuard / RolesGuard(ADMIN)
  -> DTO validation
  -> Controller
  -> Feature Service
  -> recheck administrator inside the write transaction
  -> Prisma / PostgreSQL
  -> explicit safe response
```

حراس Nest تعمل قبل ValidationPipe؛ التحقق من DTO يسبق استدعاء Controller الفعلي.
فحص الدور في بداية الطلب وحده لا يكفي لكتابة إدارية: تعاد مراجعة جلسة الفاعل وحالته ودوره داخل المعاملة.

## عقد المستخدمين المقترح

كل المسارات تحت /api/v1 وتتطلب ADMIN مع جلسة كاملة غير ملزمة بتغيير كلمة المرور.

| الطريقة والمسار | المدخل أو النتيجة |
|---|---|
| POST /users | email، displayName، initialPassword، role، وmerchantId عند الدور MERCHANT |
| GET /users | قائمة مقسمة إلى صفحات مع فلاتر role وisActive وmerchantId والبحث |
| GET /users/:id | تفاصيل حساب آمنة |
| PATCH /users/:id | email وdisplayName وrole وmerchantId حسب الحاجة؛ لا password أو isActive هنا |
| PATCH /users/:id/status | isActive: true أو false |

القواعد:
- الأدوار الأربعة الحالية فقط؛ لا محرر صلاحيات مخصص أو أدوار ديناميكية في هذه المرحلة.
- البريد يطبّع ويكون فريدًا؛ displayName غير فارغ بعد trim.
- initialPassword تخضع لسياسة PasswordService الحالية، وتحفظ Argon2id، ولا تعاد في الاستجابة أو السجل.
- كل حساب جديد يبدأ mustChangePassword=true. المدير يحدد كلمة مرور أولية خاصة ويكون تسليمها للمستخدم خارج API؛ لا إرسال بريد أو إشعارات.
- createdById من حساب المدير الموثوق؛ لا يُقبل من الطلب.
- MERCHANT يحتاج merchantId لتاجر موجود وفعّال. الأدوار الأخرى يلزمها merchantId=null.
- عند التحويل من MERCHANT لدور آخر يجب إرسال merchantId=null صراحة؛ وعند العكس يلزم معرف التاجر.
- تغيير الدور أو البريد أو ارتباط التاجر يبطل جميع جلسات الحساب داخل المعاملة نفسها. تعديل الاسم وحده لا يبطلها.
- تعطيل المستخدم يبطل جميع جلساته؛ إعادة تفعيله لا تعيد إحياء الجلسات المبطلة.
- لا يمكن تعطيل آخر ADMIN فعّال أو إنزاله لدور آخر حتى عند تنفيذ طلبين بالتزامن.
- يجوز للمدير تغيير دوره أو تعطيل نفسه إذا بقي مدير فعّال آخر؛ تنتهي جلسته نتيجة العملية.
- لا تعديل كلمة مرور حساب قائم هنا؛ تغيير المستخدم لكلمته موجود، واستعادة/إعادة التعيين برمز أحادي الاستخدام تحتاج شريحتها المستقلة.
- الاستجابة بقائمة حقول صريحة: id، email، displayName، role، merchantId، isActive، mustChangePassword، createdById، createdAt، updatedAt. لا hash أو جلسات أو رموز.

## عقد التجار المقترح

| الطريقة والمسار | المدخل أو النتيجة |
|---|---|
| POST /merchants | code وname وphone |
| GET /merchants | صفحات وبحث وفلاتر isActive |
| GET /merchants/:id | بيانات التاجر |
| PATCH /merchants/:id | name وphone فقط |
| PATCH /merchants/:id/status | isActive: true أو false |

القواعد:
- code يختاره المدير مرة واحدة؛ trim ثم uppercase، وبعد التطبيع حروف A–Z بطول 2–8 وفريد.
- لا يوجد حقل code في DTO التعديل؛ محاولته ترفض، وTrigger القاعدة الحالي يظل حماية إضافية.
- الاسم والهاتف غير فارغين مع احترام أطوال الشيما. الهاتف نص للمحافظة على + والأصفار؛ لا افتراض بلد أو صيغة أرقام محلية.
- إنشاء التاجر لا ينشئ حساب دخول تلقائيًا؛ التاجر مالك البضاعة، وقد ترتبط به عدة حسابات.
- تعطيل التاجر يبطل جلسات حساباته الحالية داخل نفس المعاملة. تبقى حالة isActive لكل حساب كما هي، حتى لا يضيع التعطيل الفردي.
- إعادة تفعيل التاجر لا تعيد الجلسات القديمة ولا تفعل حسابًا معطلًا فرديًا.
- لا حذف نهائي، ولا حسابات تاجر أو مخزون أو أرصدة ينشئها النظام ضمن بيانات اختبار التطوير.
- مسارات الإدارة ADMIN فقط. ما تحتاجه عمليات المخزن لاحقًا من قراءة قائمة التجار يصمم كصلاحية قراءة صريحة مع ميزات الأعمال، وليس توسعة ضمنية لهذه الواجهات.

## التزامن وإعادة التفويض
1. الكتابات الإدارية تستخدم قفل PostgreSQL استشاريًا ثابتًا مشتركًا داخل transaction؛ العمليات الإدارية قليلة ولا تشمل حركات المخزون المستقبلية.
2. تقفل صفوف المستخدمين المتأثرين، ومعهم الفاعل، بترتيب UUID ثابت. الجلسات الحالية تستخدم قفل صف المستخدم نفسه.
3. تعاد مراجعة جلسة الفاعل وحالته وكونه ADMIN وعدم إلزامه بتغيير كلمة المرور بعد انتظار القفل.
4. عند تعطيل تاجر، تقفل حساباته قبل تعديل حالة التاجر وإبطال الجلسات، بترتيب موحد مع بروتوكول المستخدمين.
5. عمليات ربط حساب بتاجر أو إنشاء حساب وتعديل التجار تستخدم القفل الإداري نفسه؛ لا تظهر حسابات جديدة خارج مجموعة الإبطال أثناء التعطيل.
6. تعد قاعدة آخر مدير بعد القفل، ثم تنفذ الكتابة والإبطال ذريًا. فشل أي جزء يرجع كل العملية.
7. فحص كلمة المرور وتجزئتها عند إنشاء حساب يتم قبل فتح المعاملة؛ التفويض الحاسم يعاد داخلها.
8. وقت الإبطال من قاعدة البيانات. لا ثقة بوقت أو هوية يرسلها العميل.

هذه إضافة لبروتوكول الكتابة الإدارية داخل PostgreSQL الحالي؛ لا Redis أو distributed lock service.
إذا كشف التنفيذ تعارضًا في الأقفال أو حاجة لتغيير التصميم المعتمد، تتوقف الجزئية لعرض التعديل قبل استكمالها.

## المدخلات والأخطاء والقوائم
- رفض الحقول الزائدة وUUID غير صالح وPATCH فارغ.
- فلاتر boolean تقبل true/false صراحة، ولا تستخدم تحويلًا يجعل النص false صحيحًا.
- صفحة افتراضية 1، حجم افتراضي 25، حد أقصى 100؛ ترتيب ثابت createdAt ثم id.
- 400: مدخل غير صحيح أو علاقة role/merchantId غير صحيحة.
- 401: جلسة غير صالحة أو حساب غير فعّال.
- 403: دور غير مسموح أو إلزام تغيير كلمة المرور.
- 404: الحساب/التاجر المطلوب غير موجود، بعد التحقق من صلاحية الإدارة.
- 409: بريد/رمز مكرر أو عملية تزيل آخر مدير فعّال أو ارتباط جديد بتاجر معطل.
- لا رسائل SQL أو تفاصيل داخلية في الاستجابة.
- تسجل أحداث الأمان بالفاعل والهدف ونوع العملية دون كلمة المرور أو token. هذه logs أمنية؛ دفتر حركات المخزون الدائم غير القابل للتعديل شريحة أعمال لاحقة.

## اختبارات القبول
- المدير ينشئ ويقرأ ويعدل؛ أمين المخزن والموظف والتاجر يمنعون من كل واجهات الإدارة.
- جلسة mustChangePassword لا تدير حسابات أو تجارًا.
- البريد/رمز التاجر المكرر تحت التزامن يعطي نتيجة واضحة دون خطأ داخلي مكشوف.
- فحص تطبيع البريد والرمز وثبات رمز التاجر وحدود الحقول ورفض الحقول السرية.
- إنشاء MERCHANT دون تاجر، أو دور موظف مع merchantId، أو ربط بتاجر معطل يرفض.
- الحساب الجديد له منشئ موثوق وكلمة مرور مجزأة وإلزام تغيير؛ لا تسرب initialPassword.
- الدور والبريد والتاجر عند تغييرهم يبطلون الجلسات؛ الاسم وحده لا يفعل ذلك.
- التعطيل وإعادة التفعيل لا يعيدان صلاحية رمز قديم.
- تعطيل تاجر يبطل حساباته فقط، ولا يؤثر على تاجر آخر أو يفعل حسابًا معطلًا فرديًا عند إعادة التفعيل.
- تعطيل/إنزال آخر مدير يرفض؛ محاولتان متزامنتان لا تتركان النظام بلا مدير فعّال.
- فاعل سحبت صلاحياته أثناء انتظار المعاملة لا يستطيع إكمال كتابة إدارية.
- دخول متزامن مع التعطيل لا يترك جلسة صالحة بعد إكمال التعطيل.
- فشل الإبطال أو التحديث يتراجع ذريًا دون نصف عملية.
- الصفحات والفلاتر لا تسرب حقول الأسرار ولا تكرر عناصر نتيجة ترتيب غير ثابت.
- إعادة اختبارات المصادقة والشيما الحالية والبناء والفحص.

الاختبارات على قاعدة عشوائية مستقلة فقط؛ لا إنشاء حسابات تجريبية في stocked_dev.

## حدود المرحلة
