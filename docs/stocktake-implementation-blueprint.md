# الجرد والمواقع وقفل التعديلات — Blueprint مقترح

التاريخ: 9 أكتوبر 2026. الحالة: **اعتمد المستخدم التصميم وأذن بالتنفيذ في هذه المحادثة؛ نُفذ محليًا في 9 أكتوبر 2026**.
النطاق: stocked-backend فقط؛ لا تعديل Flutter، ولا حزم جديدة، ولا نشر إنتاج. طُبق الترحيل المعتمد على stocked_dev المحلي بعد نسخة احتياطية وفحوص ومقارنة البيانات.

## الغرض والقرارات المؤكدة

إتاحة جرد شامل للمخزن، أو لتاجر بكل أرففه، أو لصف بكل أرففه، أو لرف محدد. يمكن للتاجر امتلاك عدة أرفف وإضافة غيرها لاحقًا. عند فتح أي جرد تتوقف جميع تعديلات التشغيل والإدارة للجميع، بمن فيهم المدير. العرض وإجراءات الجرد تبقى متاحة. أمين المخزن يستطيع إجراء الجرد؛ المدير وحده يعتمد ويغلق، أو يلغي بسبب موثق دون تغيير الأرصدة. تسجيل الحاضرين والملاحظات والقائم بالعد والمعتمد وتوقيت كل إجراء. جميع التسويات اليدوية وفروق الجرد، زيادة أو نقصان، للمدير فقط.

## التدفق السابق عند إعداد التصميم — قبل تنفيذ هذه المرحلة

```text
HTTP → SessionGuard / PasswordChangeGuard / RolesGuard → DTO → Controller
 → خدمة العملية → StockMutationService.run
 → قفل مفتاح العملية → قفل المستخدم وإعادة التحقق من التفويض
 → أقفال التاجر/الصنف/المستند → StockPostingService.lockBalances
 → مستند + StockMovement → تحديث InventoryBalance → commit
```

- `src/inventory/stock-mutation.service.ts`: معاملة وأقفال منع تكرار العمليات وإعادة التفويض؛ لم يكن به قفل جرد عند إعداد التصميم.
- `src/inventory/stock-posting.service.ts`: قفل رصيد الصنف على مستوى المخزن، منع السالب، وتحديث الإسقاط.
- `src/items/items.service.ts`: الإنشاء له معاملة مستقلة؛ تعديل الصنف يستخدم `AdminMutationService`.
- `src/auth/admin-mutation.service.ts`: حسابات وتجار وبعض تعديلات الأصناف؛ قفل إدارة عام ثم أقفال مستخدمين مرتبة.
- `src/stock-adjustments/stock-adjustments.controller.ts` و`stock-adjustments.service.ts`: كان المدير والأمين يستطيعان التسوية قبل هذه المرحلة، ومصدرها حركة `RECEIPT_IN` فقط.
- خدمات الشحنات: التسجيل والتجهيز لا يخصمان؛ الخروج يثبت `SHIPMENT_OUT` ويحدث الرصيد.
- خدمات المرتجعات: الاستلام عهدة فقط؛ فحص GOOD أو قبول NOTED يثبت `RETURN_IN`؛ المعلق والمرفوض ليسا رصيدًا متاحًا.
- `prisma/schema.prisma`: لا صفوف أو أرفف أو أرصدة مواقع. مفتاح الرصيد الحالي مخزن + صنف.
- ترحيلات دفتر المخزون تفرض عدم تعديل التاريخ وتطابق الرصيد مع دفتر الحركات؛ إضافة أعمدة وحدها لا تكفي.
- لا خريطة Graphify خاصة بالباك إند موجودة وفق الفحص الحالي. استُخدمت خريطة الملفات في BACKEND_PROGRESS ثم المصادر المحددة أعلاه.

## نقطة التغيير

1. الجرد الجزئي يحتاج معرفة كمية الصنف داخل الموقع، لا مجرد قائمة أرفف للتاجر.
2. القفل يجب أن يدخل كل معاملات التعديل قبل أي قفل إدارة/مستخدم/صنف؛ فحص HTTP منفرد قابل للسباق.
3. فروق الجرد تحتاج مصدرًا صريحًا مرتبطًا بالجرد، دون اختلاق مرجع استلام أو تعديل حركة قديمة.

## الهيكل ومسؤوليات الخدمات المقترحة

نبقي نمط Nest الحالي: Controller → DTO → خدمة مسؤولة عن عملية → Prisma/SQL. لا Repository أو UseCase إضافيين.

| الخدمة المقترحة | مسؤوليتها |
| --- | --- |
| `OperationalWriteGateService` في وحدة مستقلة صغيرة | أخذ قفل معاملات موحد وفحص حالة منع التعديلات؛ لا إدارة جلسات ولا قواعد جرد |
| `StorageLocationsService` | إدارة صفوف وأرفف وملكية الرف والتحقق من صلاحية الموقع |
| `StockPlacementService` | توزيع حركة مخزون على المواقع والتحويل الداخلي والتهيئة الموثقة، وأقفال أرصدة المواقع |
| `StocktakeOpeningService` | فتح دورة واحدة، تثبيت النطاق ولقطة الأرصدة والحاضرين |
| `StocktakeCountingService` | تسجيل العد وإعادة العد والملاحظات والحضور وإرسال الدورة للمراجعة |
| `StocktakeApprovalService` | تحقق المدير من العد، تثبيت تسويات الفروق والإغلاق وفك القفل ذريًا |
| `StocktakeCancellationService` | إلغاء المدير للدورة مع السبب والتاريخ دون تسوية |
| `StocktakesReadService` | عرض الدورات والبنود والفروق والسجل مع عزل ملكية التاجر |

`StockMutationService` و`AdminMutationService` يظلان مسؤولين عن التفويض ومعاملاتهما؛ يستدعيان بوابة الكتابة أولًا. لا تُدمج إدارة الجرد أو الأرفف فيهما. `StockPostingService` يحتفظ بمسؤولية الرصيد الإجمالي، وتستخدم خدمات العمليات `StockPlacementService` لتحديث مواقع نفس الحركة داخل نفس المعاملة.

Widget Tree: لا ينطبق؛ هذه مرحلة API فقط. لا شاشات أو تغييرات مقاسات Flutter ضمن النطاق.

## نموذج البيانات المقترح

الأسماء التالية مقترحات تنفيذ للاعتماد:

- `StorageRow`: مخزن، رمز ثابت فريد داخل المخزن، اسم وحالة نشاط.
- `StorageShelf`: صف، مخزن، رمز ثابت فريد داخل المخزن، تاجر مالك واحد، نشاط وهوية ووقت الإنشاء. التاجر قد يملك عدة أرفف في صفوف مختلفة. لا نقل ملكية رف به رصيد أو عهدة؛ يعطّل فارغًا ويحفظ تاريخه.
- `StockPlacementBalance`: رصيد صنف/تاجر/مخزن/رف؛ قيود تمنع ملكية خاطئة والسالب. الإجمالي الحالي يساوي مجموع أرصدة الأرفف وأي كمية غير موزعة.
- سجل توزيع ثابت يربط كميات الموقع بحركة المخزون الأصلية، مع مستند تحويل داخلي ذي طرف مصدر ووجهة. التحويل الداخلي لا يزيد أو ينقص إجمالي المخزن ولا يظهر كتسوية كمية.
- `Stocktake`: رمز، نوع ونطاق، حالات `COUNTING / PENDING_APPROVAL / APPROVED / CANCELLED`، فاتح الدورة ووقته، المدير الحاضر، الملاحظات، المعتمد/الملغي والوقت والسبب. دورة نشطة واحدة للنظام الحالي حتى لو نطاقها جزئي.
- `StocktakeScope`: المواقع والتجار المجمدون عند الفتح مع snapshots للأكواد والأسماء؛ تغيير الملكية لاحقًا لا يغير تاريخ الجرد.
- `StocktakeLine`: صنف + موقع، كمية دفترية ثابتة، آخر عد صالح، الفرق وسبب الفرق. صفوف الأصناف غير النشطة ذات الرصيد لا تُستبعد.
- `StocktakeCountEntry`: عد وإعادة عد كسجلات ثابتة، مع المنفذ واسم snapshot ووقت قاعدة البيانات وملاحظاته وتسلسل مراجعة. الصفر عد صريح؛ عدم العد ليس صفرًا.
- سجل حضور وملاحظات وأحداث ثابت: تسجيل الإضافة/التصحيح/المراجعة والإلغاء والاعتماد؛ لا حذف لإخفاء إجراء.
- `StockAdjustment`: مصدر محدد يدوي باستلام أو فرق جرد. مرجع استلام اختياري فقط لفرع الجرد، ومرجع بند الجرد إلزامي له. قيود XOR ومطابقة التاجر والصنف والمخزن والكمية، وتسوية واحدة لكل بند ذي فرق. تستخدم الحركات الحالية `ADJUSTMENT_IN/OUT` مع المصدر الموثق.

لا سجل حركة عندما الفرق صفر. فقد على رف وزيادة على رف آخر يسجلان كبندين مستقلين مرتبطين بالجرد، حتى لو صافي الصنف صفر؛ لا ندمجهما بما يخفي مكان الفرق. لا تنشئ عملية الجرد SKU جديدًا لصنف مجهول أو تابع لتاجر آخر.

## إعداد المواقع وربط العمليات

هذه مرحلة لازمة قبل جرد رف موثوق، وليست إدارة أرفف شكلية:

- الاستلام الأول: توزيع كامل كمية كل بند على أرفف تاجر الصنف.
- الخروج: تحديد الأرفف المسحوب منها والتحقق من مجموع المسحوب مقابل بنود الشحنة؛ لا حجز كميات عند تسجيل الطلب أو التجهيز.
- GOOD بالفحص أو قبول المرتجع: تحديد أرفف دخول الرصيد المتاح داخل المعاملة نفسها.
- التسوية اليدوية: المدير يحدد رفًا صحيحًا بجانب المصدر والسبب، ويحدّث الرصيد المحلي والإجمالي.
- النقل بين أرفف التاجر: مستند مستقل ثابت، لا تسوية ولا تغيير في الإجمالي؛ ممنوع أثناء الجرد.
- المعلق وغير المفحوص والمرفوض يبقى عهدة منفصلة عن المتاح. يضاف موقع العهدة وسجل نقلها ليمكن تفسير الموجود فعليًا في الرف، وتظهر في الجرد بقسم مستقل للملاحظة والعد. فروق عهدة المرتجع لا تتحول تلقائيًا إلى تسوية الرصيد المتاح؛ تحفظ كملاحظة تحتاج مسار معالجة مستقل. `MISMATCH` لا يعد على SKU المتوقع.

### الأرصدة القائمة

لا نفترض أن قاعدة التطوير أو قاعدة مستقبلية فارغة. الترحيل لا ينسب رصيدًا قديمًا إلى رف مختلق، ولا ينشئ حركة افتتاحية جديدة. الكميات القائمة تبقى في مجموعة صريحة «غير موزع على رف» لكل تاجر وصنف. المدير ينفذ توزيعًا موثقًا على مواقع حقيقية دون تغيير مجموع المخزون. حتى يكتمل التوزيع يمنع فتح الجرد لتجنب إظهار جرد شامل ناقص. العهدة القائمة تحتاج كذلك توثيق موقعها قبل جرد مواقعها. إن لم توجد أرصدة/عهدة فعلية لا توجد تهيئة كميات.

## دورة الجرد والصلاحيات المقترحة

| الإجراء | من يملكه |
| --- | --- |
| فتح الجرد وتسجيل النطاق والحاضرين | المدير أو الأمين؛ تسجيل مدير حاضر إلزامي |
| العد وإعادة العد والملاحظات والحضور | المدير أو الأمين المعيّن في الدورة |
| إرسال للمراجعة | المدير أو الأمين المعيّن |
| إعادة الدورة للعد مع السبب | المدير فقط |
| اعتماد الفروق وإغلاق الدورة | المدير فقط |
| إلغاء من COUNTING أو PENDING_APPROVAL | المدير فقط، بسبب إلزامي |
| تغيير الأرصدة بتسوية يدوية خارج الجرد | المدير فقط |

الموظف والتاجر للقراءة حسب الصلاحيات الحالية؛ لا صلاحية عد جديدة للموظف في هذا المقترح. تسجيل حضور المدير توثيق بشري، وليس ادعاء أن API تثبت وجوده الفعلي. الاعتماد يتطلب تأكيد المدير للحضور ومراجعته النهائية. كل عرض للتاجر مقيد ببنوده فقط، ولا يكشف حضورًا أو بيانات غير لازمة من تجار آخرين.

المدير يفتح من جديد بعد الإلغاء إن أراد جردًا آخر؛ لا استئناف دورة ملغاة بعد السماح بحركات مخزون، لأن اللقطة أصبحت تاريخية. انقطاع الشبكة/الخادم لا يلغي الدورة تلقائيًا ولا يفك القفل.

## القفل تحت التزامن

- حفظ حالة الجرد النشط في قاعدة البيانات؛ لا قفل ذاكرة ولا معاملة مفتوحة طوال ساعات الجرد.
- كل كتابة تشغيل/إدارة تأخذ **قفل معاملات مشترك** لهوية عالمية ثابتة، ثم تفحص الحالة. إن توجد دورة نشطة تُرفض بـ409 ورمز `STOCKTAKE_ACTIVE`.
- فتح/اعتماد/إلغاء الجرد يأخذ **القفل الحصري لنفس الهوية**. الفتح ينتظر انتهاء الكتابات التي دخلت قبله، ثم ينشئ الدورة واللقطة في معاملة واحدة. نقطة بدء الجرد هي نجاح تثبيت المعاملة، لا لحظة ضغط الطلب.
- طلب تعديل بدأ قبل الفتح ولكنه لم يحصل على القفل بعد، يفحص الحالة بعد انتظار القفل، فيرفض إن ثبت الجرد قبله. لا يعاد تشغيل طلب مرفوض تلقائيًا بعد الاعتماد.
- ترتيب الأقفال: بوابة التشغيل → أقفال الإدارة/مفتاح العملية → المستخدمون بترتيب ثابت → مستند الدورة/المستند التشغيلي → التاجر/الأصناف → أرصدة المواقع والإجمالي بترتيب ثابت. لا محاولة لترقية قفل مشترك إلى حصري.
- عمليات العد تأخذ القفل المشترك ثم تتحقق من الدورة والصلاحية والحالة، وتقفل بند العد وتستخدم رقم إصدار متوقع. اعتماد/إلغاء بالقفل الحصري ينتظران العد الجاري، ويمنعان أي عد متأخر.
- قيد SQL يمنع دورتين نشطتين. قيود وتحقق SQL تحمي مصادر تسويات الجرد والدفتر والرصيد المحلي والإجمالي عند commit. حماية التعديل العام ليست مجرد Guard للواجهة.

## حدود العرض فقط والاستثناءات المقترحة للاعتماد

ممنوع للجميع: استلام، تسجيل وتجهيز وخروج الشحنات، كل عمليات المرتجعات، التسويات اليدوية، نقل كميات، إنشاء/تعديل/تعطيل الأصناف والتجار والمستخدمين والمواقع. التاجر والمدير لا يملكان تجاوز القفل.

مسموح: GET للبيانات حسب الصلاحية، إجراءات دورة الجرد، تسجيل الدخول والخروج، تجديد lastSeen للجلسة، عدادات حماية الدخول والسجل الأمني. **أقترح السماح بتغيير كلمة مرور المستخدم لنفسه كجزء من إجراءات الدخول** كي لا تُغلق جلسة مدير مجبر على تغييرها؛ هذا استثناء يحتاج اعتمادًا صريحًا ضمن التصميم، وليس تعديل حسابات إدارية. مهام صيانة قواعد الأعمال لا تتجاوز البوابة؛ لا migration أو bootstrap أثناء جرد نشط.

## تدفق البيانات المقترح

```text
عملية مخزون + توزيع الأرفف
 → معاملة واحدة → دفتر إجمالي + سجل مواقع → رصيد إجمالي + أرصدة أرفف

فتح جرد → قفل حصري → نطاق ولقطة ثابتان + حضور → منع الكتابات
 → عد موثق لكل صنف/رف → مراجعة أسباب الفروق والحضور
 → اعتماد المدير → تسويات مصدرها الجرد + الحركات + تحديث رصيد الرف والإجمالي
 → APPROVED وفك القفل في نفس commit

إلغاء المدير + سبب → CANCELLED وسجل ثابت + فك القفل
 → لا حركات ولا تغيير أرصدة
```

## الاعتماد والفشل

يتطلب الاعتماد عدًا صريحًا لكل بند، سببًا لكل فرق، ملاحظات ختامية وتأكيد حضور المدير، وعدم وجود تعارض إصدار. أي عد إضافي يخص صنفًا معروفًا لنفس التاجر ورفًا في النطاق؛ يضاف بلقطة صفر موثقة إذا لم يكن موجودًا في رصيد الرف. حساب الفرق: المعدود - الدفتري.

الاعتماد يقفل الدورة وأرصدة البنود، يتحقق من التفويض بعد الانتظار، وينشئ التسويات والحركات وتوزيعاتها ويحدث الأرصدة ويغلق الدورة ويفك القفل في معاملة واحدة. خطأ أي بند يرجع الجميع ويترك الدورة نشطة للمراجعة. إعادة نفس مفتاح الاعتماد ترجع النتيجة السابقة دون خصم مزدوج. طلب اعتماد وطلب إلغاء متزامنان لا ينجحان معًا. فتح وإلغاء واعتماد تستخدم Idempotency-Key وعقد replay واضحًا؛ أي replay لا ينشئ تعديلًا جديدًا ويتحقق من التفويض.

## خطوات التنفيذ بعد الاعتماد

1. تثبيت العقود وتفاصيل نموذج المواقع والجرد والقيود الجديدة.
2. تنفيذ بوابة الكتابة واختبارات السباق ودمجها في كل معاملات التشغيل والإدارة.
3. تنفيذ المواقع والتوزيع والتهيئة والتحويل وعقد توزيع العمليات الحالية واختبار تطابق الإجمالي.
4. تنفيذ فتح الجرد واللقطة والحضور والعد والمراجعة والقراءة.
5. تنفيذ اعتماد المدير وتسويات المصدر الجديد والإلغاء، وقصر التسويات الحالية على ADMIN.
6. اختبار القبول والتزامن والملكية وقاعدة البيانات، ومراجعة مستقلة عند توفر إذن Antigravity.
7. توثيق النتائج؛ أي تطبيق لترحيل محلي يكون بعد تحقق البيئة وخطة حفظ البيانات، ولا نشر إنتاج ضمن هذه المرحلة.

## التحقق المطلوب

- جرد تاجر له عدة أرفف، جرد صف ورف، وصنف في عدة مواقع؛ عدم تسرب تاجر آخر.
- عد صفر، عدم عد، إعادة عد متزامنة، أسباب الفروق، موجود إضافي معروف، أصناف غير نشطة، حدود الأعداد.
- منع التعديلات من المدير والأمين والموظف؛ إنشاء أصناف وتعديل حسابات وتجار مع الطلبات السابقة للفتح.
- استثناءات الدخول تبقى صالحة؛ القراءة لا تضيف عمليات تجارية.
- دورتان متزامنتان، عد أثناء اعتماد/إلغاء، اعتماد مزدوج، retry بعد فقد الرد، سقوط الخادم واستمرار القفل.
- فرق موجب وسالب وصفر، صافي صفر بين رفّين، فشل بند وسط الاعتماد والتراجع الكامل.
- الإلغاء يحفظ التاريخ دون تغيير رصيد؛ منع تعديل العد/الحضور/الملاحظات بعد الإغلاق.
- مجموع المواقع يساوي الإجمالي ودفتر الحركات؛ نقل داخلي بلا تغيير إجمالي؛ منع الملكية الخاطئة بالسورس وSQL.
- توزيع الأرصدة السابقة لا يزيد المخزون؛ العهدة المعلقة والمرفوضة لا تُضاف للرصيد المتاح.

الأوامر المخطط لها ولم تنفذ في مرحلة التصميم:
`npx prisma validate`، تنسيق الملفات المتأثرة فقط، `npm run lint`، `npm run build`، `npm test`، `npm run test:e2e -- --no-file-parallelism`، `npm run test:db`، `git diff --check`.
لا build منفصل بالتزامن مع e2e؛ لا reset أو حذف volumes؛ لا اتصال إنتاج.

## الاعتماد الذي صدر قبل التنفيذ

اعتمد المستخدم التصميم وأمر بالتنفيذ بكامل أثره على المواقع وتوزيع الكميات وعقود العمليات، بما يشمل: رف لتاجر واحد، فتح المدير أو الأمين مع تسجيل مدير حاضر، العد للمدير/الأمين المعيّن، الاستثناء الأمني لتغيير كلمة المرور الذاتية، معالجة العهدة منفصلة دون تسوية مخزون، ومنع الجرد حتى اكتمال توزيع الكميات القائمة.

أذن المستخدم لاحقًا صراحة بإرسال الملفات اللازمة إلى Antigravity للقراءة والبحث والكتابة المساندة، مع بقاء التصميم والأمان والمنطق والتنفيذ والمراجعة النهائية لدى Codex. جرت محاولتان للبحث للقراءة فقط بنموذجين متاحين، إحداهما على نسخة مصادر معزولة دون أسرار أو بيانات عملاء؛ كلتاهما توقفتا بسبب RESOURCE_EXHAUSTED 429. لم يصل تقرير بحث، ولا ادعاء تقييم مستقل ناجح. تولى Codex التحقق المصدري والتنفيذ والمراجعة النهائية.

راجع [عقد الجرد النهائي](stocktakes-api.md) و[عقد المواقع](storage-locations-api.md) للتفاصيل الفعلية، خصوصًا مواقع عهدة المرتجعات ومصادر سحبها وتسلسل الأحداث ومفاتيح إعادة الطلب.
